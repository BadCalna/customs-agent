# 首期方案评估（Astra 意见整理）

> 整理日期：2026-11-04
> 前提条件：几十行一批、11/18 交付、允许使用云端模型

---

## 一、结论

**值得做。两周内可以做出一个有真实核验能力的演示版本，用于 AI 创意大赛。2 核 4GB 作为起步配置够用。**

但这是"试点配置判断"，尚未压测。

首期定位：**备品备件申报资料的智能预审与审核分流平台。**

必须证明的一件事：**减少专家反复检查和供应商反复补资料的工作量。**

---

## 二、创意为什么成立

优势来自业务闭环，不是技术。痛点具体：货品杂、供应商填报质量低、沟通分散、专家重复审核、时间集中在下半个月。有明确用户、真实输入、可比较的工作结果。

最有说服力的演示：上传一张真实脱敏表格 → 系统指出哪些行有问题、缺什么、依据是什么、下一步谁处理 → 供应商补充后展示修改差异 → 专家复核完成。

---

## 三、三个必须先补的窟窿

| 缺口 | 问题 |
|---|---|
| **"填得对"定义不清** | 字段填满、商品描述合理、HS 归类正确，是三个不同层次 |
| **参考数据未分层** | 当期税则、归类依据、申报要素要求、企业历史记录，不能当成同一种知识管理 |
| **没有效果基线** | 能展示功能，不等于能证明价值。缺审核时间、返工轮次、漏检情况的数据 |

比赛评分标准未知，因此无法预判获奖概率。

## 四、分流机制：对应业务动作，不用综合分

| 分流结果 | 典型情况 | 下一步 |
|---|---|---|
| 待补资料 | 关键材质、用途、规格缺失，无法判断 | 输出逐行补数清单，专人联系供应商 |
| 待专家重点复核 | 信息较完整，但编码与属性冲突、候选有争议、依据不足 | 专家查看疑点及相关证据 |
| 待常规复核 | 信息完整，关键属性与依据一致，无明显冲突 | 专家快速确认 |

## 五、四条硬约束

1. **先逐行判断，再汇总整批。** 99% 看起来正常，也不能掩盖剩下那一行。首期由人工决定整批退回还是部分送审。
2. **历史申报成功只是参考。** 要比品牌、完整型号、材质、用途等关键属性，以及适用版本。新品不一定有问题，旧品也不能直接放行。
3. **先查编码合理性，再核该编码对应的申报要素。** 否则供应商选错编码后，把错误编码要求的字段全填满，系统照样判合格。
4. **模型自报"95% 置信度"不能作为分流依据。** 分流条件必须来自可检查的规则，并用专家标注样本验证。

法定依据：现行商品归类规定要求依据税则条文、归类规则和相关注释，结合货物实际状态确定归类。历史记录只能辅助，不能替代依据。
https://policy.mofcom.gov.cn/claw/clawContent.shtml?id=101348

## 六、技术选型

**Python + Django，一个应用完成首期。**

| 部分 | 选型 | 用途 |
|---|---|---|
| 后端 | Django 5.2 LTS（最新安全补丁） | 账号、权限、审核流程、数据管理 |
| 页面 | Django 模板 + HTMX，少量 JS | 上传、结果表格、筛选、审核操作、进度刷新 |
| 数据库 | PostgreSQL | 审核任务、文件版本、商品行、历史记录、依据、修改版本、审核记录 |
| Excel | openpyxl | 读标准模板，导出问题清单和审核结果 |
| 后台任务 | Django-Q2（复用 PostgreSQL 存队列） | 批量预审、失败重试，避免网页长时间挂起 |
| AI | 公司认可的云模型 API，首选百炼千问 Plus 系列 | 属性整理、语义矛盾识别、候选比较、补数说明 |
| 部署 | Nginx + Gunicorn + 独立后台任务进程 | ECS 上跑网页与预审任务 |

选 Django 的理由：现在需要的是带账号、资料、审核流程的平台，Django 自带的数据库管理、账号权限、内部管理后台能省掉大量组装工作；供应商和专家走独立设计的业务页面。

Django-Q2 复用数据库存任务，当前任务量下可以少维护一个 Redis；但仍要配超时和重试，并保证重复执行不覆盖人工已确认的结果。

前端不拆 Vue/React。首期只有上传、看问题、复核、导出，模板页面够用，也能做成已有原型那种工作台外观。

参考：
- https://docs.djangoproject.com/en/5.2/intro/overview/
- https://docs.djangoproject.com/en/5.2/topics/auth/default/
- https://django-q2.readthedocs.io/en/master/brokers.html#django-orm

## 七、AI 流水线（固定步骤，不做动态编排）

```
表格解析 → 确定性规则校验 → 检索历史及适用依据 → 模型分析 → 程序校验结果 → 分流
```

- 必填、格式、单位等确定性检查交给程序。
- 模型负责理解描述、发现语义矛盾、解释疑点。
- 模型返回固定字段，程序再校验完整性和合法性。格式正确 ≠ 业务判断正确。
- 百炼支持结构化输出，但不同模型支持范围不同。https://help.aliyun.com/zh/model-studio/qwen-structured-output

**首期不引入**：多 Agent、独立向量数据库、复杂工作流平台。历史资料先按品牌、型号、关键属性查询；真样本证明检索不足，再考虑语义检索。

### AI 的用武之地（规则做不了的部分）

字段非空、格式、单位、编码位数这些检查交给程序，更快更稳更省钱。AI 只负责语义层：

| AI 承担 | 为什么规则做不了 | 业务后果 |
|---|---|---|
| 判断"这套信息够不够定码" | 字段非空 ≠ 可归类。继电器按电压分三档，填了 125A 照样定不了码 | 减少"看着填全、其实没法判"的假合格 |
| 从自由文本抽取属性 | 供应商在规格/备注写一整段话，需拆成材质、品牌、型号、用途 | 不必回头逼供应商按格式重填 |
| 发现跨字段语义矛盾 | 品名"不锈钢螺丝"、材质列写"碳钢"；品名"轴承"、用途写"电柜" | 这类矛盾人工漏检率最高 |
| 俗名、错别字归一 | "固体继电器"是"固态继电器"的错写；"电柜"是用途不是品类 | 编码与依据才能正确命中 |
| 生成供应商看得懂的补数说明 | "缺材质"没人会补；"内外圈是不锈钢还是轴承钢？请拍铭牌"才有人回 | 直接决定返工轮次能否下降 |

### AI 不碰的三件事

1. 不输出置信度作为分流依据。
2. 不直接决定这一行走哪条通道——只产出结构化事实与疑点清单，分流由规则基于这些事实计算。
3. 不替代归类依据。历史记录只是参考，依据仍是税则条文与归类规则。

一句话：**AI 负责发现，规则负责决策。** 这样每个分流结果都能倒查——专家问"凭什么判它待补资料"，能指到具体缺失字段和具体条款，而不是"模型觉得"。

### AI 是否只是装饰：一个必须先测的比例

- 若真实表格中 **70% 以上**的问题是"字段空白、单位错、编码格式不对" → 本质是校验工具，AI 是装饰，讲不出故事。
- 若 **60% 以上**是"信息不足、描述含糊、跨字段打架" → AI 是主角，价值主张成立。

**这个比例目前无人知道。** 拿到真实样本后，手工把问题分两类数一遍，两小时能出结果。这比再讨论三天技术方案有用。

> 验证案例（取自知识沉淀第五节）：
> - 固态继电器 125A：字段全填，程序判合格；AI 能识别 125A 是电流非型号、缺电压无法定码 → 这才是 AI 的活。
> - 热过载继电器 LRD12C：型号本身不含电压信息，须读规格书才知道 >60V。
> - 深沟球轴承 6224/C3：C3 是游隙代号，属型号组成部分。同样是"规格"字段，一个填型号、一个填电流参数，程序看到的是同一个字符串。

## 八、复杂度判断

技术中等，可靠归类判断明显更难。

| 工作内容 | 难度 | 主要难点 |
|---|---|---|
| Excel 导入、缺项检查、结果导出 | 低—中 | 字段映射、准确定位原始行 |
| 历史匹配、AI 疑点识别与分流 | 中—高 | 匹配条件、证据质量、误判控制 |
| 专家复核、退回、重新提交 | 中 | 版本管理、状态流转、审核留痕 |
| 备品备件稳定准确归类 | 高 | 商品知识复杂、关键资料缺失、依据适用性 |
| 多供应商正式接入、报关草单生成 | 中—高 | 数据隔离、业务口径、字段来源与单证规则 |

AI 编程工具能加速页面、数据库、导入导出。**专家判断标准、真实样本、验收，仍需要你和业务人员投入时间。**

许可提醒：WorkBuddy/Qoder 的使用许可，与平台可调用的模型 API，是两件事，分别落实。开发前确认接口、账号、额度即可，不必现在锁定模型型号。

## 九、2 核 4GB 的边界

模型在云端跑，本机只处理网页、数据库、表格。几十行的任务不必先买更大配置。

- 后台先限 1～2 个处理任务，逐行或按小批次保存结果。
- 几千行可以排队，但不能承诺秒级：模型响应时间、调用限额、费用可能比服务器算力更早成为瓶颈。
- 验收时用典型几十行 + 最大几千行两类样本，分别测耗时、内存、失败重试、网页响应。
- 上传要限文件大小，不能只按行数判断负担。

## 十、11/18 最小闭环

**保留**：标准模板上传、逐行预审、三类分流、依据与补数说明、人工确认或退回、重新上传后的版本记录、结果导出。

**推到后续**：自动消息通知、发票箱单处理、报关草单生成。

供应商通知继续人工完成。比赛版可以由内部人员代上传以降低交付压力；若要展示供应商登录，用预开演示账号，并验证供应商之间的数据隔离。

| 时间 | 完成内容 |
|---|---|
| 11/4—11/5 | 定模板、选少数典型品类、拿真实脱敏样本和模型接口 |
| 11/6—11/9 | 打通上传、规则校验、结果页面、人工复核、导出 |
| 11/10—11/12 | 接入历史检索、适用依据、模型分析，完成分流 |
| 11/13—11/15 | 专家验证独立样本，修正误判，测重试与版本处理 |
| 11/16—11/17 | 冻结功能，准备对比数据和演示材料，完整彩排 |
| 11/18 | 提交与展示 |

前提：你能持续投入开发，且前两天拿到样本和专家支持。主要靠零散业余时间，就要进一步压缩品类和页面数量。

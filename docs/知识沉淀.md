## 零、当前已确认的业务流程（2026-11-12）

> 本节与需求目录中的流程图、网页端功能要点和Skill共同记录当前口径。下方11步全流程、钉钉H5双端方案、三表综合识别与物流终审是历史讨论；旧原型尚未实现本次两阶段流程。

**当前范围起点：采购合同签订完成。主要载体：网页端应用。当前范围终点：专家审核通过；后续动作待补充。** 专家是否由物流岗位担任待配置，不额外预设一次物流审批。

```text
采购合同签订完成
  → 供应商上传Excel，系统解析并保留版本
  → 上传后自动预审
  → 主品名＋别名＋规格＋厂家型号＋对应附图，AI独立推荐HS
  → 申报要素页：海关编码（供应商）→ AI推荐HScode → 预审结论
  → 业务员退回/导出让供应商补充，或提交指定版本给专家
  → 专家核要素、附图、退税率及适用税则/归类/两用等法规
  → 专家确认通过，或选择具体退回对象、责任人和问题清单
  → 任何补料重传都整表重新预审，再交专家；旧审批不沿用
  → 专家通过后的动作：待补充
```

| 环节 | 责任角色 | 输入与输出 | 关键控制 |
|---|---|---|---|
| Excel上传 | 供应商 | 装箱明细、申报要素及附图；供应商HS/要素/退税率原值 | 上传解析后自动预审；原件、版本、历史意见及图片保留 |
| HS预审 | 系统自动、AI辅助 | 独立归类后比较供应商HS，在原编码右侧连续放AI推荐HScode和预审结论 | 同码但缺关键证据仍无法确认；差异与待补原因、置信度完整说明 |
| 补料或提交 | 业务员、供应商 | 业务员退回/导出，供应商补资料重传，或业务员提交专家 | 导出不等于已退回/已通知；新资料绑定新版本 |
| 专家审核 | 专家、AI辅助 | 要素与图片/规格逐项核，退税按编码/日期/官方税务政策核，相关法规可追溯 | 专家置信度单独保存；明确不匹配原因、条款条件及补料对象 |
| 专家处置 | 专家 | 通过或指定责任方及问题退回 | 任何补料重传都整表重新预审；旧版通过不自动沿用 |

**关键字段**：合同第一条品名为主品名；附件清单品名为别名；规格与厂家/供应商型号分来源联合使用，按合同号＋项号定位申报行附图。只读两个目标页签；箱件汇总随原文件保留。“场景提供型号”暂按此前厂家/供应商提供型号理解。不能从生产商推品牌，也不能从图片推成分、工艺或退税率。

**当前建议状态**：待上传 → 上传解析后自动预审 → 预审执行中 → 待业务员处理 → 待供应商补充 / 待专家审核 → 专家核查 → 专家通过 / 专家退回。系统执行失败单记异常，不伪装成商品错误。AI建议、人工状态、预审置信度、专家置信度及监管状态分别保存。

**证据口径**：海关税则/归类规则核商品分类，税务/财政政策核出口退税，商务部等有效清单及法规核两用等监管。图片只辅助确认货物及可见要素；关税税率不等于出口退税率。实际引用标题、条款、URL、适用日期及商品条件，缺证据就写待核，不能编造。专家决定退回给业务员、供应商或已明确的责任方，AI不自动派发。

**已确定（2026-11-13）**：供应商使用本人账号登录上传；首期仅一名专家、不分派；站内消息，业务员与专家节点通过钉钉 DWS 通知；系统不填拟申报日期；结果页为商品行＋卡片布局。**仍待定**：专家与物流人员映射、退回责任人选择范围、专家通过后的交接/知识回流时点。当前细节见`AI辅助申报要素与HS归类/网页端功能要点.md`及其skills目录。

## 一、历史业务流程基线（11步，保留作背景）

> 2026-11-05新增需求见“网页端功能要点.md”的“品名建议与物流确认”：用户要求原品名和建议品名并列展示，物流确认最终品名。建议须真实、准确，无法提出准确建议时注明原因；敏感及管控风险不因名称变更消除。当前项目仍为静态演示资料，登录、上传持久化、后台识别和物流审核须由服务端落地。

```
ERP拟签 → 采购合同签订 → 货物申报要素制作 → 物流文员审核 → 货物到货
→ 报关单据制作 → 报关预录单核对 → 完成报关 → 大副收据核对
→ 提单草本核对 → 确认提单正本
```

各环节关键点（人工核对重点）：

| 环节 | 关键字段 |
|---|---|
| 货物申报要素制作 | HS编码是否正确、申报要素是否完整且合理 |
| 报关单据制作 | 重量、件数、品名 |
| 报关预录单核对 | 重量、件数、品名、境内货源地 |
| 大副收据核对 | 重量、件数、品名 |
| 提单草本核对 | 重量、件数、品名、船名、航次 |

## 二、业务痛点（会议共识）

1. **最大痛点：申报要素与HS归类的"准确性瓶颈"**——上游乱填（供应商填写不准、配合度低）、中游没能力核（业务员缺乏归类专业能力与动力，如焊丝/焊条退税差异）、下游没时间核（货到后申报，工作堆积在最后两周，物流单人判断、风险集中末端）。
2. **结构性痛点：货到后申报 → 时间极度压缩**，全员高强度加班。
3. 申报要素识别错误会引发外部合规风险（海关质疑、退税损失、扣货退运）。

## 三、AI全流程重构方案（项目定位：全流程重构，非单点赋能）

**三条重构主线：**
1. 申报准备前移——合同阶段即生成申报任务、按到港时间倒排提醒，到货前完成要素制作与审核；
2. 核对能力产品化——重量/件数/品名等关键点全部AI自动比对，人工只处理标红异常；
3. 知识库贯穿——每次审核通过的申报自动回流沉淀，AI推荐优先命中历史记录。

**双端载体：**
- 业务员端：钉钉H5微应用（品名+规格+图片录入 → AI推荐HS编码与申报要素 → 缺失字段补数清单可转发供应商）；
- 物流/审核端：网页工作台（申报单AI预审、Excel批量导入异常标注、单证比对差异报告、知识库管理）。

**AI推荐可信度分级规则（核心业务规则）：**
- 高置信度：命中企业历史申报成功记录或官方税则精确匹配 → 直接确认提交；
- 中置信度：仅第三方数据源匹配 → 标注"待官方核验"，物流端复核；
- 低置信度：多候选得分接近或关键归类字段（电压/材质/成分）缺失 → 不给唯一推荐，生成补数清单；疑难项提示申请海关预裁定（署令236号）。

**单证核对基准（跨页规则）：**

| 核对环节 | 基准单据 | 关键字段 |
|---|---|---|
| 报关单据制作 | 合同+发票+装箱单（三单交叉校验） | 重量、件数、品名 |
| 预录单核对 | 报关单据 | 重量、件数、品名、境内货源地 |
| 大副收据核对 | 报关单据+装箱单 | 重量、件数、品名 |
| 提单草本核对 | 大副收据+报关单据+订舱信息 | 重量、件数、品名、船名、航次 |

## 四、HS编码数据源策略（不采购，自建知识库）

- **官方公开渠道**：海关总署「互联网+海关」进出口税则查询（customs.gov.cn → 政务服务 → 我要查）、中国国际贸易单一窗口（singlewindow.cn → 参数查询）、海关总署公告栏目（增量更新来源）、「海关归类一指通」微信公众号、12360热线；
- **官方无开放API**，只能页面抓取+人工兜底；税则每年集中调整一次，更新负担可控（年度全量 + 公告增量）；
- **申报要素清单最难拿**：官方不提供批量下载——所以企业历史申报记录是最独特资产；
- 第三方HS编码库（hsguilei.com、i5a6.com、hsbianma.com 等）数据整理自海关公开数据，**仅作初筛层，不可作为合规依据**，须以官方当期数据核验；
- 架构：企业历史申报数据（RAG主力）+ 官方税则数据 + 海关公告解读 + 预裁定/归类决定判例库。

## 五、已验证归类案例库（兼作AI提示词回归测试集）

| 商品 | 归类结论 | 关键经验 |
|---|---|---|
| 深沟球轴承 6224/C3（SKF） | **8482102000**，退税13%，监管条件无 | 型号即规格，C3游隙属型号组成部分；"结构类型"可由型号规则库推断；要素示例 `4\|1\|深沟球轴承\|减少摩擦，滚动支撑用\|SKF\|6224/C3\|无\|无` |
| 热过载继电器 LRD12C/5.5-8A（施耐德） | **85364900.90**（>60V，旧码85364900.00已作废拆分），监管条件A | 继电器归类第一依据是**电压**（≤36V / 36-60V / >60V 三档），品名规格看不出，需读铭牌/规格书 |
| 固态继电器 125A（"固体继电器"为错别字） | 推荐 85364900.90（中置信），**缺电压/品牌/型号无法定码** | "电柜"是用途不是品类；125A是电流不是型号；典型"信息不足"案例——AI应输出缺失字段补数清单而非硬猜 |

**规律总结**：标准化工业品（轴承）型号承载结构信息，AI易做；俗名商品（焊丝/焊条）与参数依赖商品（继电器按电压分档）才是AI价值最大的场景，需要"品名+规格+图片"三合一输入。

## 六、AI 推荐核心机制（2026-11-02 新增，网页端交互原型已实现）

### 6.1 识别分层策略（先本地、再大模型，节省时间与成本）

识别不是一次全走大模型，而是两段式：

```
第1层：查本地知识库（企业历史申报记录 + 官方税则 + 已回流数据）
        ├─ 命中 → 即时返回，不调用大模型（快、零成本、可靠）
        └─ 未命中 → 进入第2层
第2层：调用大模型（DeepSeek V4 Flash）查询公开数据加工
        └─ 产出兜底归类建议，标注"参考值"，需官方核验
```

- **为什么要分层**：本地库命中率高时，绝大多数查询走本地、毫秒级返回；只有本地库没有的新品类才消耗大模型 token，省时省钱。
- **本地库构成**：企业历史申报记录（RAG 主力）+ 官方税则 + 公告解读 + 预裁定判例 + **报关回流数据**。

### 6.2 置信度必须给出「具体理由」

置信度不能只给高/中/低标签，必须说明**为什么是这个等级**，核心区分两类原因：

| 理由类型 | 含义 | 示例 |
|---|---|---|
| **信息不充足** | 商品本身可归类，但关键字段缺失 | "缺工作电压，继电器无法定档（≤36/36-60/>60V）" |
| **找不到可靠信息** | 知识库/公开数据中无可靠依据 | "本地库及公开数据均未匹配到该品类" |

具体分级理由规则（原型已内置）：
- **高**：命中企业历史成功记录 / 回流记录，或官方税则精确匹配且规格齐全。
- **中**：命中官方税则但需铭牌核验；或仅第三方初筛；或大模型查询的公开数据（属参考值）。
- **低**：信息不充足（缺关键字段）或找不到可靠信息，不给唯一推荐，输出补数清单。

### 6.3 报关数据回流（闭环，提升本地库可靠性）

报关真正结束后，把**正确的归类结果写回本地知识库**：

- 回流内容：品名 + HS 编码 + 申报要素（真实值）。
- 回流后效果：该商品再次出现时**本地库直接命中 → 高置信度**，不再需要调大模型。
- 形成正向闭环：用得越多 → 本地库越全 → 命中率越高 → 越省时越可靠。
- 原型中用 localStorage 模拟持久化，真实版本应写回后端数据库。

### 6.4 大模型接入方案（DeepSeek V4 Flash）

- **模型 id**：`deepseek-v4-flash`（旧名 `deepseek-chat` / `deepseek-reasoner` 已于 2026-07-24 弃用）。
- **API**：OpenAI 兼容，Base URL `https://api.deepseek.com`，100 万 token 上下文，支持 JSON 输出/工具调用/思考模式。
- **架构**：浏览器 HTML 不能直连（CORS + Key 安全），需加一层**本地代理服务**（Python FastAPI）转发请求；Key 存本地 `.env`，不进前端、不进 Git。
- **降级**：代理未启动时原型回退为"模拟解析/查询"，保证演示不中断。

### 6.5 自然语言解析回填表单（输入形态的补充）

在结构化表单之上，增加「一句话描述商品」入口，形成"对话能力回流到界面"的混合式交互：

- **流程**：用户输入一段自然语言 → 模型解析出 品名/规格/型号/品牌 → **回填到表单字段**（可再改）→ 用户确认后走原有识别流程。
- **解析接口**：`/api/parse`（大模型语义解析）；未接大模型时用本地正则规则兜底（提取型号/电压/电流/品牌/品类关键词）。
- **设计定位**：这是"界面为主、对话为辅"决策的落地——结构化录入用表单（高效、可审核、可留痕），模糊/口语化表达用自然语言解析兜底，解析结果落回结构化字段，不留在聊天记录里。
- **降级原则**：解析不出的字段（如品牌）明确提示"请手动补充"，不静默丢字段。

### 6.6 产品形态决策（界面 vs 对话式）

**结论：界面为主、对话为辅，混合式。**

- 报关场景不适合纯对话：输入是结构化字段+图片、输出是表格化数据（需逐项可编辑/可标黄）、置信度分级需视觉编码、强合规场景需可追溯可审核。
- 对话式价值在"兜底追问"：品名俗名/口语化、用户不知字段含义、低置信度需解释补数原因。
- 落地：主路径表单 → 兜底入口自然语言解析 → 结论回填表单。

## 七、实现决策与排期

- 范围：**10天AI辅助开发版**，只做"申报要素与HS归类辅助"一条主线（业务员录入→AI推荐→提交→文员审核→通过入库），砍掉：Excel批量导入、单证OCR比对、转发供应商、倒排提醒、统计看板（二期增量）；
- 技术栈建议：Python FastAPI + SQLite/MySQL + 原型HTML改造；
- 关键风险：①提示词质量决定成色——用第五节三个案例做回归测试集，每次改提示词跑一遍；②铭牌图片OCR识别效果提前测，识别不准就让用户手填；
- 钉钉发布路径：企业内部H5微应用（开放平台建应用配首页URL），需要钉钉管理员开通权限；最简起步可先网页链接+账号密码登录，免登后补；
- 协作：仓库邀请Collaborators即可，与token无关。

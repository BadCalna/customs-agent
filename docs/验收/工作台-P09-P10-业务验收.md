## 7. 失败、回执丢失与恢复验收

故障矩阵应在**专用自动化库或另建复验库**执行。可使用上述原型浏览器脚本的请求拦截；它对四类写入逐一注入下列 HTTP 状态，拦截发生在请求转发前，因而可以验证该次注入没有服务端写入。这里的注入不表示正常 P09/P10 接口实际返回 501。

### 7.1 四类写入与错误状态矩阵

每一格都必须满足：明确显示实际 HTTP 状态及可用的错误码/请求编号、不显示成功、不伪造任务或商品状态。填写中的弹窗字段保持，待核对状态下阻止继续写入；刷新前先记录草稿，恢复连接并刷新后以服务端实际数据为准。整页刷新或主动取消弹窗不承诺恢复未提交草稿。

| 写入动作 | 401 未登录/会话失效 | 403 权限/CSRF | 409 修订/版本/状态冲突 | 422 参数/业务校验 | 501 未实现注入 |
|---|---|---|---|---|---|
| 逐行确认 | 不新增确认 | 不新增确认 | 不覆盖新修订 | 不保存无效编码 | 不显示确认成功 |
| 整批提交 | 不生成提交 | 不生成提交 | 不覆盖当前提交 | 不接受缺行/无确认 | 不显示提交成功 |
| 专家整批通过 | 保持待审 | 保持待审 | 不重复处置 | 不接受漏行/无改码理由 | 不显示通过成功 |
| 专家整批退回 | 不新增问题 | 不新增问题 | 不重复处置 | 不接受缺理由/跨版本商品 | 不显示退回成功 |

恢复原则：401 重新登录；403 核对身份、对象权限及会话 CSRF；409 刷新后核对最新版本、修订和提交状态，再决定是否重新填写；422 修改输入；501 保留错误证据。不得通过修改页面角色、去掉修订号或换幂等键来绕过冲突。

| 场景 | 复验方式 | 必须看到的结果及恢复方法 |
|---|---|---|
| 请求发送前断网 | 在确认弹窗填入编码和理由，拦截并中止确认请求 | 提示「本次操作结果未确认」，草稿保留，不出现成功；恢复后刷新，核对确认是否存在 |
| HTTP 200 但错误体/回执不完整 | 返回 200 错误对象或缺少本次对象标识的响应 | 不能只凭 HTTP 200 判成功；显示结果待核对，不推进页面状态 |
| 正在保存时连续点击 | 暂缓提交响应，观察并再次点击提交按钮 | 显示等待、按钮禁用，同一次操作不重复发送写请求 |
| 提交已落库，响应丢失 | 自动化将请求真实转发成功后丢弃回执 | 页面显示结果未确认，不显示成功；刷新后能找到唯一的已保存提交与正确快照；先核对，避免制造另一次业务操作 |
| 写回执已成功，随后重读失败 | 允许写请求成功，令后续 history 读取返回 503 | 明确显示「服务端已保存，但页面刷新失败，请刷新核对」，保留草稿、不显示普通成功；恢复读取后刷新，能查到原写入及其原因 |
| 页面子请求失败 | history 等子请求返回 503 | 整体显示真实读取错误；顶栏仍为 LIVE，不退回 fixture、DEMO 或混用部分旧数据作为成功结果 |
| 真实 API 重复重放 | 对同一目标，以原始相同载荷和相同 `Idempotency-Key` 重放提交/裁决 | 返回原结果的 `idempotent_replay`，不新增重复记录；同键换载荷或换目标应冲突。以 API 用例补证，不用双击模拟真正并发 |

确认采用商品 `expected_revision`；提交和裁决采用当前任务 `revision`。确认请求携带旧修订号时，即使编码相同也可返回 409；同值加当前修订号才是无新增确认记录的重放，不能用它验证「新增理由已保存」。提交/裁决的页面幂等键绑定同一目标和同一载荷，在当前页面生命周期内保持稳定；不要假定整页重载后仍保留原键。回执丢失时优先刷新读取，而非盲目重新保存。若需 API 重放，应保留并使用原始请求完整内容与原键。

「断网」本身不能证明未落库：可能是请求未送达，也可能是写入完成后回执丢失。页面的待核对提示、服务端记录和刷新结果必须共同判断。对于旧指纹格式的既存幂等记录，安全地返回 409 也不应被视作可以绕过冲突的理由。

## 8. API 与数据证据核对

在浏览器开发者工具 Network 面板检查真实请求；也可在已登录会话下打开 `/api/v1/docs` 查看契约。以下路径均位于当前验收服务，不是静态清单链接。写入需要会话 cookie 和当前 `X-CSRFToken`；登录后 CSRF 可能轮换，不能沿用旧值。普通业务账号的服务端权限仍须检查。

| 接口 | 核对内容 |
|---|---|
| `POST /api/v1/auth/login`、`GET /api/v1/me` | 真实登录、实际用户名和角色；退出后身份读取为 401 |
| `GET /api/v1/tasks/{task_id}` | `stage`、`revision`、当前版本、当前提交 ID/状态；当前人工问题不串入 V1 |
| `GET /api/v1/versions/{version_id}/items/{item_id}` | 身份、原表位置、五阶段值、确认/提交来源、专家核查目标及 `review_issues` |
| `PATCH /api/v1/versions/{version_id}/items/{item_id}/confirmation` | 请求为 `confirmed_hs`、`reason`、商品 `expected_revision`；回执确认 ID、版本/商品、确认值、商品/任务新修订均匹配 |
| `POST /api/v1/tasks/{task_id}/submissions` | 请求携带 `Idempotency-Key`，正文为 `version_id`、任务 `revision`、覆盖全部商品的 `items:[{item_id,confirmation_id}]`；回执 `status=pending`，每行 `submitted_hs` 与所引用确认一致 |
| `POST /api/v1/submissions/{submission_id}/decisions` | 请求携带 `Idempotency-Key`；回执 `decision_id`、版本/提交、动作、`submission_status`、任务阶段符合本次操作；不要把裁决回执的状态字段误读为 `status` |
| `GET /api/v1/tasks/{task_id}/history` | 逐版本的商品、确认、提交快照、裁决、问题与审计；新旧版本各自的引用完整，重放没有新增重复业务记录 |

裁决正文的关键字段：

- 通过：`{revision,action:"approve",reason,items:[{item_id,final_hs,change_reason}]}`。`items` 必须覆盖本次提交的全部商品，改码行的 `change_reason` 必填。
- 退回：`{revision,action:"return",reason,return_to:"supplier",issues:[{item_id,message}]}`。本例 `item_id` 必须为 V2 第 5 行 `8a226944-e5d7-5df5-b40a-3c84868a680d`，不能混入 V1 的同名商品 ID。

商品**卡片**中的 `business_confirmed_hs`、`submitted_hs`、`expert_final_hs` 等阶段字段形如 `{value,source_id}`，检查 `.value` 和 `.source_id`；商品**列表**同名字段为简化标量，不要混用两种响应格式。供应商原文位于卡片 `facts.supplier_hs_raw`。当前确认的 `source_id` 是确认记录 ID，提交阶段的 `source_id` 是提交 ID，最终阶段的 `source_id` 是裁决 ID。

# 网页端功能要点（当前开发口径）

更新日期：2026-11-12。当前采用“供应商上传 → 业务员预审 → 专家审核”两阶段；本节及Skill替代此前“上传即综合识别、业务定稿、物流终审”的口径。现有交互原型仍为旧演示，未实现本次两阶段逻辑；本轮先改流程及Skill。

## 1. 业务顺序与角色

| 步骤 | 角色 | 动作 | 输出与下一步 |
|---|---|---|---|
| 1 | 供应商 | 合同签订后上传Excel，提交原HS、申报要素、退税率、附图等实际资料 | 留存原文件及版本，解析装箱明细/申报要素；尚不触发归类 |
| 2 | 业务员 | 点击“预审” | 启动当前版本商品归类与供应商HS比较 |
| 3 | AI预审 | 用主品名、别名、规格、厂家型号、附图独立推荐HS，再比较供应商原HS | 在申报要素页填AI推荐HScode及预审结论；不改供应商原码 |
| 4 | 业务员 | 查看差异原因，选择退回、导出补料或提交专家 | 逐商品补料问题可追溯；导出不等于退回/已通知 |
| 5 | 供应商（按需） | 补资料、修订Excel、重传 | 新版本重新预审，业务员复核后再提交专家 |
| 6 | 专家审核AI辅助 | 基于业务员提交版本，核查原要素、附图、退税及法规 | 分项匹配结果、专家结论、专家置信度及待补/修改清单 |
| 7 | 专家 | 决定通过，或明确退回角色、具体责任人及问题 | 退回业务员/供应商整改；通过形成专家确认版本，后续动作待补充 |

专家是本轮确认的审核角色；是否由物流岗位担任待业务配置，不额外加一次物流审批。

## 2. 业务员预审：商品输入和HS比较

| 来源 | 字段 | 业务含义 |
|---|---|---|
| 装箱明细 | 合同第一条品名 | 商品主品名，不能被附件名称覆盖 |
| 装箱明细 | 附件清单品名 | 别名，帮助检索、理解和消歧；实质冲突保留并提示 |
| 装箱明细 | 规格＋厂家/供应商提供型号 | 共同组成规格型号，各自保留原文及来源；用途场景单独记录 |
| 两个页签 | 合同号＋合同项号，辅以物料/规格 | 关联同一商品，不能按同名或相同行号串联；合并申报保留成员 |
| 申报要素 | 匹配行的附图 | 真实读取可见结构和铭牌；不能拿邻行图/图片文件名冒充识别 |
| 申报要素 | 供应商海关编码 | 原码比较对象，不作为独立推理正确的前提 |

用户口述“场景提供型号”暂按此前的厂家/供应商提供型号理解。不同模板列位会变，不能把“合并申报”“特别注意”当型号；字段缺失如实提示。

预审使用官方及可追溯的第三方/历史资料，结合真实商品属性与规则给出建议。输出顺序固定：

`海关编码（供应商原值） → AI推荐HScode → 预审结论 → 原右侧字段`

- AI推荐HScode填有依据的完整10位文本码；无法唯一归类则注明暂不定码，候选及条件写结论/核查明细。
- 预审结论包含：一致/不一致/无法确认/供应商未填/编码异常/关联异常，双方编码、判断依据、具体原因、预审高/中/低置信度、待补信息和来源版本状态。
- 编码相同但缺关键参数/有效性依据，仍为“无法确认”；不同也不直接断言供应商错误。
- 新增两列应真实插入并保持相邻，原附图、公式、合并关系及历史意见随列调整保真；不能占用已有数据。
- 预审不替供应商修改原申报要素、退税率或自动更名。发现监管线索保留交专家，不隐去。

## 3. 专家审核：分项核对和法规解释

| 核查项 | 核查方式 | 不匹配/无法确认时 |
|---|---|---|
| HS分歧 | 先明确待审编码及选择依据，不默认采用AI建议 | 无唯一编码则保留条件分支，不生成虚假的最终模板/退税率 |
| 申报要素 | 对应编码官方模板最长前缀匹配，逐项比原要素、规格和附图 | 输出缺失/冲突/证据不足，写原值、证据及需改/需补内容 |
| 图片 | 比形态、供货范围、品牌/型号和铭牌可见参数 | 图未显示不等于文字错误；需本批照片/铭牌/材质证等佐证 |
| 退税率 | 商品→待审HS/适用退税代码→日期/业务条件→税务/财政官方政策→原表退税率 | 原率与官方依据并列；未取得适用数据写待核，不猜0%或具体率 |
| 归类法规 | 海关适用税则、归类总规则、类注/章注/子目注释及适用决定 | 引用实际取得标题、条款/页码、URL、生效日期及商品条件，解释为何不能确认 |
| 两用等监管 | 商务部等有效法律、条例、清单及公告与真实技术参数/用途用户等核查 | 列条目、技术门槛和缺失信息；不凭关键词、同HS或改名断言不受控 |

退税率不能与图片直接做数值匹配；关税税率不等于出口退税率。一般商品不强行套两用法条；找不到规则正文时说明待核，不能编造条号。

专家输出包括“专家审核结论”“置信度（专家审核）”、建议要素、退税核查、监管核查和补料要求。供应商原要素/原率保留；建议独立展示。每个降低置信度的原因能追溯到商品字段、事实或规则缺口。

## 4. 人工决定、版本与退回

- 业务员决定退回供应商、导出让供应商补充，或提交专家；系统只给辅助建议。业务员可将疑难问题交专家，不以AI等级代替人工决定。
- 专家退回时必须指定对象角色、责任人（可确定时）和逐商品问题。业务员处理关联/编码分歧，供应商补商品事实/要素/图片；AI建议和最终选定值分开留存。
- 任何补料重传都整表重新预审，包括仅补要素/税务证据的情况：不区分未变商品，也不能仅因只改要素列就认定不影响归类。业务员重新确认并提交后，专家重新审核；旧预审与旧审批不进入新版本，只作历史保留。行级影响判断和预审复用留作后续优化。
- 文件、分析任务及人工决定均绑定版本；旧版通过不自动授权新版。查询失败单记系统异常，不伪装成商品错误或已完成审核。

## 5. 置信度与标色

预审置信度衡量归类证据；专家置信度衡量综合核查，独立保存。高：关键事实一致且当期官方依据充分；中：类别较清楚但存在可列明缺口；低：身份/关键资料冲突、跨税目未排除或关键监管/税务条件无法支持结论。信息多但矛盾不提高置信度。

低置信度红字浅红底，中置信度黄底；待填/冲突要素红字。HS比较异常另外标状态及原因，不与置信度混成一个标签。专家要素/退税/相关监管关键项待核时，不能给整体高置信度。

## 6. 本轮边界及待定配置

- 本轮为流程及Skill修订，未改造网页原型交互，也未对具体商品重新查询、改写Excel或实施后端。
- 仅用装箱明细和申报要素作为核心商品输入，箱件汇总随文件保留；专家通过后交接、报关及知识回流时点待补充。
- 待定：专家与物流岗位的人员映射、供应商账号/代上传、退回责任人选择范围与通知方式、拟申报日期来源、正式模板中专家结果列的最终布局。以上不影响本轮已确定的两阶段规则。
- 当前流程图：`流程图/AI辅助申报要素与HS归类-flow.html`；执行规则：`skills/steel-hs-declaration/SKILL.md`；字段、结果结构及证据分工见其references。

## 以下为历史方案（2026-11-02，仅供参考）

## 一、整体定位

报关全流程（11 步）AI 化重构中的**网页工作台**，服务物流文员/物流专员，核心解决「申报要素与 HS 归类准确性」问题。

**核心识别分层策略**：先查本地知识库 → 未命中再调大模型查公开数据 → 报关后数据回流本地库，形成闭环。

---

## 二、功能模块清单

### 模块 1：单票录入与 AI 推荐

| 功能点 | 说明 | 关键要求 |
|---|---|---|
| 商品信息录入 | 品名、规格、型号、品牌、图片五类输入 | 均为非必填；图片支持上传/拖拽，最多 3 张 |
| AI 识别并推荐 | 触发归类推理，输出唯一 HS 编码 + 申报要素 | 识别过程可视化展示分层步骤 |
| 置信度分级 | 高 / 中 / 低三级 | **必须附带具体判定理由** |
| 缺失字段补数 | 信息不足时生成待补清单 | 逐项说明缺什么、为什么影响归类 |
| 候选编码列表 | 展示其他可能编码及推荐理由 | 支持切换采用 |
| 申报要素编辑 | 要素清单可逐项编辑 | 提交前可人工修正 |
| 报关数据回流 | 报关结束后将正确结果写回本地库 | 形成闭环，提升后续命中率 |

**置信度理由必须区分两类**（核心业务规则）：
- **信息不充足**：商品可归类但关键字段缺失（如缺电压无法定继电器档位）。
- **找不到可靠信息**：本地库和公开数据都无可靠依据。

---

### 模块 2：Excel 批量导入与异常识别

| 功能点 | 说明 | 关键要求 |
|---|---|---|
| 文件上传 | 支持 .xlsx / .xls / .csv，拖拽或点击 | SheetJS 本地解析 |
| 模板下载 | 提供标准导入模板 | 列名对齐：品名/规格/型号/品牌 |
| 逐行识别 | 每行执行「先本地库、再大模型」归类 | 展示进度条 |
| 异常标注 | 信息缺失/不确定的行**标黄** | 异常行视觉高亮 |
| 置信度列 | 结果表新增「置信度」列 | 高/中/低三色标签 |
| 判定依据列 | 每行给出置信度的具体理由 | 区分信息不足/找不到可靠信息 |
| 申报要素列 | 每行生成申报要素摘要 | 要素名:值的拼接 |
| 统计汇总 | 总行数/异常行数/各置信度数量 | 顶部统计卡片 |
| 导出 | 导出带标注结果 / 仅导出异常行 | 生成 .xlsx |

## 三、核心业务规则

### 3.1 置信度三级判定

| 等级 | 判定条件 | 处理方式 |
|---|---|---|
| 高 | 命中企业历史成功记录 / 报关回流记录 / 官方税则精确匹配且规格齐全 | 直接采用 |
| 中 | 官方税则但需铭牌核验 / 仅第三方初筛 / 大模型查公开数据 | 标注"待官方核验" |
| 低 | 信息不充足或找不到可靠信息 | 不硬猜，输出补数清单；疑难项提示申请海关预裁定（署令236号） |

### 3.2 识别分层流程

1. **第1层 本地库**：企业历史申报 + 官方税则 + 报关回流数据，命中即返回（快、零成本）。
2. **第2层 大模型**：本地库未命中时调 DeepSeek V4 Flash 查公开数据加工，产出标注"参考值"。

### 3.3 数据回流闭环

报关完成后将真实归类结果（品名+HS编码+申报要素）写回本地库 → 同类商品再次出现直接命中高置信度，不再走大模型。

## 四、技术要点（供开发）

| 项 | 方案 |
|---|---|
| 前端 | 单文件 HTML + 原生 JS；SheetJS 解析 Excel |
| 大模型 | DeepSeek V4 Flash（`deepseek-v4-flash`），OpenAI 兼容 API |
| 接入架构 | 浏览器不直连大模型（CORS+Key安全），需本地代理服务（FastAPI）转发 |
| Key 管理 | 存本地 `.env`，不进前端、不进 Git |
| 降级策略 | 代理未启动时回退"模拟模型查询"，保证演示不中断 |
| 本地库持久化 | 原型用 localStorage 模拟；真实版写后端数据库 |
| 待接入项 | 铭牌图片 OCR 真实识别（当前为文件名模拟） |

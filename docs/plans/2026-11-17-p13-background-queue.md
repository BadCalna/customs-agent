# P13 后台队列实施计划

目标：上传/提交不等待批量模型执行，持久登记、后台逐行处理、有限重试和中断恢复；旧版本及旧轮结果不能成为当前结果。

基线：origin/main@ad89340，独立 feature/P13-background-queue 分支。用户确认在本机独立环境验证。沿用现有 Excel 和 mock 引擎，不要求新业务资料，不修改原件、8021 测试库或 main。

设计：PostgreSQL 是状态源，django-rq/RQ/Redis 只投递 run_id。持久 RunWork 与 Run 同事务登记；后台扫描器重投待运行及租约到期记录。每次领取生成 fencing token，在 Task 锁内核对版本、执行代次和提交状态，模型调用在锁外，每行写入再次验证 token 与有效性。RunAttempt 保留每次尝试和中断；自动单行最多三次。显式人工重试创建关联旧 run 的新执行，成功行仅引用/复制已完成结果，不重新调用模型或改写旧记录。

1. 锁定 django-rq、RQ、Redis 客户端版本；扩展配置、RunWork/RunAttempt 和迁移，保留 inline 模式兼容。
2. 先增加派发丢失、重复投递、失败行、旧轮晚到、旧版本/撤回和对象权限测试，记录失败基线。
3. 实现事务内登记、提交后安全派发、后台扫描、租约恢复、逐行执行及有限退避重试；上传与提交接入可选择的执行器。
4. 发布重新预审/失败行重试端点、显式授权能力及当前进度/尝试记录，更新契约与统一客户端。
5. 在本机隔离目录启动 PostgreSQL、Redis、worker、扫描器和 Web；使用独立库与端口，不配置系统服务。经检查，RQ 2.6.1 的 SpawnWorker 仍调用 Windows 不支持的进程 API；本机使用真实 Redis + 独立 SimpleWorker 进程，记录其无子进程强制超时的边界，Linux 部署仍用默认 Worker。
6. 验证真实上传/提交及时返回、后台进度、杀 worker 后恢复、重复投递、多连接争抢、同版重跑及 V1 晚到；相关旧测试回归。
7. 更新 D4/D5/D6 与 P13 交接，记录软件来源、版本、启动停止步骤、已验证和未验证边界。提交开发分支，不推 main、不自动合并。

接口决定：保留已有 RunStatus 口径，部分失败以 progress.failed 表达。自动触发沿用任务包约定；业务员显式预审也提供正式端点，供后续页面配置使用。当前仍为 mock 模型，队列通过不代表归类质量通过。

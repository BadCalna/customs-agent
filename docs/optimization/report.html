01

优先处理什么

P0 涉及审核与会话边界；P1 影响日常操作；P2 影响阅读偏好。

优先级改进项验收时要回答的问题
P0独立登录入口与会话隔离未登录或会话过期时，能否在不暴露此前任务的情况下重新登录？
P0保留规则与可靠性保护切换任务或版本、出现异常或重复操作时，数据与写入是否仍属于当前范围？
P1找到任务、判断下一步任务队列的检索范围是否明确？操作无结果、受限或失败时，用户知道下一步做什么吗？
P1读懂数据，并能回到原始依据汇总是否限定当前版本，缺失是否被误当作一致、完成或低风险？
P2主题选择与可读性切换主题后能否辨认状态、看见焦点，并在再次打开时保留偏好？
02

同一入口，前后对照

此处「前」只指基线的根路径工作台，不指组件演示页或早期原型。

场景前 · 基线表现后 · 分支结果
独立登录页直访 /login/ 返回 404；根路径靠 hidden 切换同页表单与工作台。旧表单已支持自动填充、错密后重试。未登录访问 / 由服务端转至独立的 /login/；表单旁是港区集装箱图，不渲染任务列表。登录后回到工作台，只携带指定任务和版本。
主题青绿色固定配色。页面没有供用户切换并保存外观的控件。两页共享「海港青」「档案棕」「夜航蓝」；当前浏览器仅保存主题值，不保存登录资料。禁用本地存储时，本页仍能切换。设计组自测 5 种宽度 × 3 种主题无页面横向溢出。
操作队列已有刷新、游标翻页和选中任务高亮；每次追加 50 条，没有工作台内的搜索或阶段筛选。关键词按名称、任务编号、供应商查找已加载任务；阶段条件由服务端过滤。分别提示无可见任务、无匹配、读取中和读取失败；可直接重置。每一页按任务编号去重，过时响应不覆盖新筛选。
数据商品表已有原编码、AI 建议、业务确认、专家终值及逐条比较；运行区已显示完成、失败及处理中计数。概览把「有编码的商品数 / 本版完整明细数」与供应商原码比较分开。可由最多 3 条需核对示例打开商品及来源行。缺字段和未知状态分别列示；行重复、归属不明或数量不符不显示统计，不用零代替。
规则与可靠性预审规则有选取范围，但若把未选第 8 条的分隔符从 8. 写成 8)，解析器会把内容拼入已选第 7 条。遇到歧义便拒绝加载，不构造模型请求。14 个结构不合法的合成样例由接受变为拒绝；合法规则选段的哈希没有变化。

04

哪些结论有实测支撑

按测试对象与环境记录证据，区分自动化、人工观察和未测事项。

预审规则装载｜离线解析回归

规则组本机回归 110 项全部通过。合成反例覆盖重号、断序、竞争标题、材料包替换锚点缺失或重复；另验多行正文与 CRLF。基线与分支对合法文档选出的规则正文 SHA-256 均为 6c35d88a086261cbadd007c067a595acf235ba984525fa4cb846f380e7788bda。这证明提取范围受保护，不证明 HS 结论正确。

数据口径｜6/8 不等于 7/8

同一份合成 V2 单证有 8 条商品：运行记录是 7 条执行成功、1 条失败，商品字段却仅有 6 条给出预审建议编码。两种商品口径：建议覆盖 6/8 ≠ 运行成功 7/8。两者都不是审批通过率。比较结论为编码一致 1、编码不一致 1、待核对 3、原码缺失 1、原码异常 1、尚无结论 1。V1 另有 2 条，不跨版本相加。

数据模块七项子测试全过；组件独测在 320、390、768、1440 像素宽度与三种主题交叉的 12 种组合下未见横向溢出，未发现未捕获脚本错误。该测试不等同于全站无障碍认证。

浏览器复核｜相同场景，不伪造响应

对基线归档和候选运行源码分别启动 Django；临时 SQLite 内执行迁移并导入相同的合成样例。浏览器走真实本地登录、会话、CSRF 和 API；AI 结果是持久化的 inline mock，不是浏览器拦截替换。契约样例没有原始导入作业，其 import 404 属预期，不能将本轮样例当成真实文件解析验收。

留存基线 8 张、候选 14 张视口截图，哈希见两侧原始记录。候选浏览器实测快照的运行源码指纹为 18e2f03a477695381191031faae47dac1f28bf9e409bdbe942efcc0894587a9c，它不是 Git 提交号。A1 分别核对基线历史名「关务审核工作台」与改名候选「关务预审工作台」。

工作台交互｜定向回归

7 个新增测试与 17 个既有测试全部通过。覆盖多词检索、已加载页去重、筛选响应乱序、连续点击商品、循环游标、权限缺失、轮询版本不符及过期会话。以上是定向自动化，与下面全套统计有交集，不相加计算。

工程回归｜集成验证

SQLite 核心套件比基线多 9 项通过，跳过数不变。基线发现 1,977 项：1,930 通过、47 跳过；候选发现 1,986 项：1,939 通过、47 跳过。两轮均为 0 失败、0 错误。改名后候选的 Django 系统检查与 uv 锁文件检查均正常。

以下为改名前原工程回归（非 d2877a1 重跑）：隔离的真实 PostgreSQL 环境另跑 P21，29/29 通过；P22 运维脚本发现 83 项，80 通过、3 跳过，未实跑容器灾备恢复。跳过不算通过，上述套件不与核心结果相加。详见工程测试摘要。

06

已知限制与签收边界

代码、受控样例和真实业务的证明力不同。

  • 审核边界。界面计数和颜色不是正式归类意见。真实商品的税号、申报要素和政策依据须由有权限的业务与关务人员复核；结构校验没有改变任何法定归类规则。
  • 设备与用户。手机队列仍较高，点选任务后可见版本，但查看下方商品详情仍需滚动。上传、审批写入和导出文件也不在这 20 项的浏览器评分范围。独立审计只覆盖本地 Chrome 的桌面和触摸模拟，未覆盖真实 iOS Safari、屏幕阅读器人工验收或真实用户任务耗时；不宣称效率提升了某个百分比。
  • 数据规模与上线。3 个可见任务、V2 的 8 条与 V1 的 2 条是受控样例，不是经营量。尚不能据此推断大批量时延、真实模型准确率、完整灾备恢复或已生产部署。

建议的下一步签收：先用获授权、脱敏的已知结论样本核对全流程（P0），再由供应商、业务员、专家分别在目标浏览器验证操作（P1），最后做大批量延迟和真实恢复演练（P1）。这些均不计本轮得分。

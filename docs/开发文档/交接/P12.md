## 关键实现决定

1. **保留现有数据，不丢演示库**。按 Jay 的选择走“备份 + 复制 + 升级 + 比对”，源 SQLite 只读：
   脚本复制一份工作副本、在副本上补迁移再导出；`backup.sh` 先落 `.local/backups/`，原库不删不改。
2. **本机集群独立于 Homebrew 默认集群**。数据目录 `.local/pgdata`、socket `.local/pgsocket`、
   端口 5432 只监听回环；`trust` 认证只适用于本机开发，共享/生产必须改 `scram-sha-256`。
3. **默认后端仍是 SQLite**。`CUSTOMS_DB_BACKEND` 未设时行为完全不变；设成 `postgres` 却缺变量
   时启动即失败，避免“以为切了其实还在 SQLite”。
4. **`dumpdata` 会静默丢精度，迁移改用自研导出**。Django 的 `DjangoJSONEncoder` 对 datetime 做
   `r[:23]` 截断，只保留毫秒（`django/core/serializers/json.py`）。实测第一次迁移时
   `created_at 10:08:29.868824` 变成 `.868000`，而数量、外键、页面都看不出异常。`dumpdata_full.py`
   直接用 `serializers.serialize("python")` 拿原始值再按完整 `isoformat()` 写出，`loaddata` 侧由
   `parse_datetime` 按 6 位微秒解析。
5. **比对前必须归一 UUID 与 jsonb 形态**。SQLite 把 UUID 存成 32 位十六进制、PG 返回 `UUID` 对象；
   JSON 在 SQLite 是文本、在 PG 是 `jsonb`（键序会重排）。`verify_copy.py` 统一成 hex、解析后按键排序，
   浮点保留 12 位小数，避免把“表现差异”误报成“数据丢失”。
6. **恢复必须以业务角色执行**。第一次演练用超级用户 `pg_restore --no-owner`，恢复出来的表归 `postgres`，
   `customs_agent` 读自己的库直接 permission denied；改成以 `CUSTOMS_PG_USER` 连接恢复后正常。
7. **`check-postgres` 只认 `connection.vendor == postgresql`**，端口能连通、能 `psql` 都不算切换通过。

## 双库行为差异（实测，不是推测）

| 行为 | SQLite | PostgreSQL | 影响与处理 |
|---|---|---|---|
| `CharField.max_length` | 不校验，300 字符可写入 | 报 `DataError`（value too long） | 演示/合成数据切库前要检查超长字段；`tests/p12/test_schema.py` 锁住两边行为 |
| ASC 排序中的 NULL | 排最前 | 排最后 | 列表顺序断言不能写死；用例按后端分别断言 |
| `JSONField.__contains` | `NotSupportedError` | 走 `jsonb` 包含查询 | P16 若要按 JSON 内部字段过滤，必须要求 PG 后端 |
| 并发写入 | 单写者，`select_for_update` 空操作 | 行锁生效 | P09 并发确认实测：一个成功、另一个 409 `stale_revision`，`Confirmation` 只多一行 |
| 唯一约束竞争 | 串行化，冲突少 | 真竞争 | 并发提交同版本只落 1 份快照；20 连接 `F()` 自增无丢更新 |
| datetime 精度 | 文本存 6 位微秒 | `timestamptz` 6 位微秒 | 精度本身一致，**丢精度发生在 Django JSON 序列化**（见决定 4） |
| `LIKE`/`icontains` 大小写 | ASCII 不敏感 | 区分 | 当前 `apps/` 无 `icontains`；`tests/p12/test_types.py` 锁住精确匹配区分大小写 |
| 索引/约束可见性 | 弱 | `pg_constraint`/`pg_indexes` 可查 | `tests/p12/test_backend.py` 直接查目录：6 个唯一约束、1 个检查约束、2 个索引、外键 > 10 |

## 复跑命令

```sh
cd ~/PycharmProjects/customs-agent-p12

# 1. 起本机集群（已装过 postgresql@17 则只需 start）
scripts/database/pg_ctl.sh start
scripts/database/pg_ctl.sh status

# 2. PostgreSQL 专项检查（后端不是 PG 会直接失败）
CUSTOMS_DB_BACKEND=postgres CUSTOMS_PG_NAME=customs_agent CUSTOMS_PG_USER=customs_agent \
  make check-postgres

# 3. 双库对照报告（写到 .local/p12/dual-db-report.md）
CUSTOMS_PG_NAME=customs_agent CUSTOMS_PG_USER=customs_agent scripts/database/dual_db_check.sh

# 4. 现有 SQLite 数据迁移 + 核对（--fresh 只允许对本机开发库用）
CUSTOMS_SQLITE_PATH=.local/db-source.sqlite3 scripts/database/backup.sh pre-migrate
CUSTOMS_PG_NAME=customs_agent CUSTOMS_PG_USER=customs_agent \
  scripts/database/copy_sqlite_to_pg.sh .local/db-source.sqlite3 --fresh

# 5. 备份与恢复演练（恢复到独立库，不动业务库）
scripts/database/backup.sh drill
scripts/database/restore.sh "$(ls -dt .local/backups/*/ | head -1)/pg-customs_agent.dump" customs_agent_restore
CUSTOMS_DB_BACKEND=postgres CUSTOMS_PG_NAME=customs_agent_restore CUSTOMS_PG_USER=customs_agent \
  .venv-customs/bin/python scripts/database/verify_copy.py --skip-source

# 6. 在 PG 上跑真实 HTTP 场景
CUSTOMS_DB_BACKEND=postgres CUSTOMS_PG_NAME=customs_agent CUSTOMS_PG_USER=customs_agent \
  make dev BIND=127.0.0.1:8020
BASE=http://127.0.0.1:8020 .venv-customs/bin/python tests/p09/manual_check.py
BASE=http://127.0.0.1:8020 .venv-customs/bin/python tests/p10/manual_check.py

# 7. 回退到 SQLite：改回 CUSTOMS_DB_BACKEND=sqlite（旧库一直没动过）
scripts/database/pg_ctl.sh stop
```

# P23 官方参考数据导入流水线

状态：**待合并**（分支 `feature/P16-official-reference-import`，基线 `origin/main@5fd0d4a`）
本包把用户已取得的官方资料转换成 P14/P17 能**真实查询**的 JSON 快照，并提供
「原件盘点 → 来源清单 → 格式解析 → 字段转换 → 校验 → 导入报告 → 候选快照 →
查询验证 → 显式发布」的可重复流程。

**能读成什么、不能读成什么**：真实数据已经导入并在本机用真实适配器查通（17 项查询检查
全部通过，见第 5 节），但**没有经过任何真实关务人员复核**，因此所有结果保持
`authoritative=false` / `applicability=unknown` / `declaration_ready=false`。
本页任何“通过”都不等于“可以拿来申报”。监管条件表、进口关税与增值税仍未提供，
本包**没有**生成对应数据，也没有用空白或 0 顶替。

### 3.2 原件与来源

- 读前后各算一次 **SHA-256 与字节数**，与清单声明逐字比对；不一致 → `SourceFile.verified=False`
  → 构建直接失败（退出码 2），不“修一下继续”。导入结束再核一次，原件变了就丢弃临时目录、不发布。
- 每条记录都带 `source.document`（原文件名）+ `source.locator`（`页签!单元格`）、`retrieved_at`、
  以及来源声明的 URL；URL 只填来源里真实写了的，没有就留空。
- **导入时间与政策生效时间分开**：`generated_at`/`published_at` 只进报告与索引，不参与业务指纹；
  政策有效期只来自来源（退税率用 N/O 列），来源没给就留空。
- 真实数据、原件副本、报告、发布物全部写入 `.local/reference-import/`（Git 忽略），
  **没有向公开仓库新增任何真实数据文件**（新增的只有来源清单这类脱敏元数据）。

### 3.3 编码与语义

- 编码**按字符串处理**：文本单元格原样保留前导零；数值单元格只有“十进制整数且长度正好 8/10”
  才采用（此时不可能丢前导零），**9 位/科学计数法/浮点一律拒绝**并给出
  `HS_CELL_NUMERIC_PRECISION_LOST`，不补零、不猜位。8 位记为 `subheading`（税目/子目），
  10 位记为 `declaration`，其它长度拒绝。
- 不凭前缀扩造 10 位编码；`chapter/heading/subheading` 只按位置切分（`[:2]/[:4]/[:6]`）。
- 复用 P14/P17 的 `SourceKind`/`Authority`/`ReviewStatus`/`VersionWindow`/`SourceRef` 语义：
  官方来源 → `authority=authoritative`，但**未复核** → `DatasetInfo.authoritative` 属性为 false。
- **要素类型 ≠ 必填**：来源的 `必填标记（1/0）` 是必填声明，1→`required`、0→`optional`；
  其它值整份清单拒绝（不猜成“条件必填”）。条件文本、取值枚举**不写**（来源没有），
  `value_type` 一律 `text`。
- 退税与关税分库：退税率写 `p17.taxrate.1`，关税/增值税**未导入**。
- 三态分开：`conditions` 字段**不写**＝来源未声明（→ P17 `not_declared` → `applicability=unknown`）；
  监管 `measures` 字段在台账里根本不存在（不写 `[]`）；来源明确声明“无”的情形本批没有出现。
- 监管方向不猜：因为没有方向字段，**不生成 P17 监管记录**。

### 3.4 标准化与校验（拒绝而不是跳过）

| 检查 | 行为 |
|---|---|
| 表头识别 | 按**表头文字**定位页签与表头行，支持表头不在第 1 行；必需列缺失 → `header_not_found`；同名表头重复 → `header_ambiguous`；多个页签都满足时用“可选列命中数”区分，**仍打平就报歧义** |
| 编码 | 空/非数字/长度不对/数值精度可疑 → 该行 `rejected` + 逐条原因 |
| 必填标记 | 非 1/0 → 整份要素清单拒绝（`ELEMENT_SCHEMA_REJECTED`），**不产出缺几项的清单** |
| 重复 | 同 `(版本, 编码)`、同 `(版本, 编码, 方向)` 视为同业务键；内容一致 → `duplicate`（不产生重复记录） |
| 冲突 | 同业务键内容不同 → `conflict`：保留先出现的一条，**报告两条的来源定位并转待核**，不静默覆盖 |
| 统计数核对 | 来源自带 `申报要素数/必填数` 与明细行数不一致 → `ELEMENT_COUNT_MISMATCH`（待核，不改写数据） |
| 日期 | 退税率生效/失效日必须是 ISO；非法 → 该行 `rejected`；失效早于生效 → 拒绝 |
| 定位 | `document`/`locator` 去不可见字符后必须非空（P14/P17 加载期会再校验一次） |
| 计数对账 | 每个数据类别强制 `input_total == imported+duplicate+conflict+pending+rejected+not_imported`，对不上直接让构建失败 |
| 退出码 | `0` 成功 / `1` 部分拒绝（有 rejected、conflict、缺失输入或验证未通过）/ `2` 失败；报告里另写 `status=success/partial/failed` |

**计数单位**（报告 `input_unit` 字段明示）：税则目录=税号行；要素=要素明细行 + 目录中应有但缺失的清单
（输出单位是编码的要素清单）；退税=退税率行；注释=注释条目。

### 3.5 快照与发布

- **候选快照**：`candidates/<batch>-<业务指纹前 12 位>/`，含 5 份数据 JSON + `sources.json` +
  `manifest.json`（输出文件 sha256/字节/记录数/指纹）+ `report.json` + `report.md`。
- **稳定**：业务指纹 = `转换器版本 + 版本配置 + 各数据集业务内容`；`generated_at`、报告时间、
  复核状态不参与。输入相同 → 同一目录，**不产生第二份数据**。
- **原子**：先写 `candidates/.tmp-*` 再 `os.replace` 到最终目录；中途失败删临时目录，
  旧快照不受影响（测试覆盖）。
- **快速复用**：清单里的原件哈希 + 转换器版本 + 版本配置组成**输入指纹**，命中既有快照就不再
  解析几万行（实跑：首次约 60 s，重复运行约 26 s，且只在扩展名层面重跑查询验证）。
- **发布**：`published/releases/<release_id>/` 不可变目录 + `current.json` 指针 + `current` 软链。
  发布门禁：① 快照自检（输出文件哈希与索引一致）② 查询验证全部通过 ③ 批次必须是 `real`
  ④ 提供复核文件时必须 `decision=approved`、`reviewed_by` 非空、`reviewed_at` 带时区，
  且**对本快照的每条业务假设逐项确认**。
- **未复核也能发布，但不会被当成已复核**：数据集 `review_status` 保持 `unreviewed`，
  P14/P17 因此仍然 `authoritative=false`。**程序不会填复核人**，也不把“程序校验通过”写成“专业复核通过”。
- **不覆盖已发布版本**：待发布内容与当前版本不同时默认拒绝，必须 `--allow-content-change
  --reason ...`，并在 `release.json` 写入逐数据集增/删/改计数与样例。
- **回滚**：`releases` 列出全部发布与当前指针，`activate --release-id` 只改指针，旧 release 目录保留。

### 3.6 品目注释

- 先核实了现有适配器**没有**消费方：`adapters/`、`apps/`、`tests/` 里没有任何注释正文的字段或检索入口。
- 因此产出**独立、版本化**的快照 `p23.commentary.1`，由 `adapters/sources/tariff_commentary.py` 读取：
  `lookup(key)` 支持 `0101`（品目）、`CH1`（章注）、`CA1`（类注）、`ot3`（其他注释），另有关键词子串检索；
  结果带 `engine_integration="not_wired_p16"`，明示**已导入、尚未接入 P16**。
- 正文**逐字保留**，按 `sections[]` 保存 `类注/章注/总注释/品目注释/子目注释` 及其 `anchor`，
  不做固定长度切分、不改写为模型结论；`text_all` 与分段重新拼接的一致性在导入期核对，
  正文哈希/长度在**读取期**再校验，不一致直接报存储不可读。
- **不能当 10 位编码存在性依据**：`tariff_no` 只是品目/章/类层级键；读取接口传 8/10 位编码
  直接 `invalid_input`，并说明原因。
- 不引入向量库/Embedding/检索框架。

## 7. 未验证、风险与待办

1. **没有任何真实专业复核**：本批数据 `review_status=unreviewed`。`reviewed` 只在示例复核文件下
   验证过机制；真实复核必须由关务人员签署（D6 §2.7 的复核步骤）。
2. **版本窗口是推导值**：来源没有税则公告生效/失效日期，税则/要素版本窗口起点取**采集日期**
   （`2026-11-16`），退税率版本窗口取本批记录生效/失效日期极值（`2005-01-01`～`2100-12-31`）。
   两者都写进了 `label` 与报告假设，**不是**公告生效日；复核时需逐项确认。
3. **`state=active` 是假设**：来源是“现行税则查询结果”，未逐条声明作废/并码；因此没有
   `expired`/`merged` 记录，新旧对照表缺失。假设键 `code_state_active` 需复核确认。
4. **要素顺序不是官方顺序**：`order` 取明细行序，仅用于稳定排序与定位。P14 的位置式原文解析
   （`0|1|品牌：…`）在顺序未被专家确认前**不得作为判定依据**。
5. **条件必填/取值枚举缺失**：`0` 不等于“任何情况下都非必填”；P14 的 `sufficient` 只有在
   专家补齐条件口径后才有意义。
6. **退税率仍不能作依据**：来源没有适用条件列 → `conditions_state=not_declared` →
   `applicability` 恒为 `unknown`；447 条「11 位细分税率不同」另记 `rate_state=unknown`。
   要真正可用，需补政策条件与 11 位细分口径。
7. **8 位回退的映射口径**：9,777 条退税率是税务文库按 8 位码命中、按来源逐行映射到 10 位税号，
   已在记录 `note` 与证据定位里标注；若专家认为不能这样映射，应改为只保留 8 位码记录
   （会让 10 位查询查无）。
8. **监管条件不可用**：`p17_regulatory` 明确 `not_provided`；`regulatory_codes.json` 只是原文台账，
   不进入 P17、不得据此判断“无监管”。
9. **品目注释未接入 P16**：只提供确定性查找与子串检索；没有检索排序、没有评测。
10. **进口关税/增值税/新旧对照表/口径文件**仍未提供，未做任何推断。
11. **性能**：首次导入约 60 s（解析 92 万单元格 + 生成 130 MB JSON），重复运行约 26 s；
    未做并发与增量更新，年度换版按“新增版本文件、旧版本保留”的方式做。
12. **越界风险**：本包不改现用 `.env`、不部署、不合并 PR；发布物在 Git 忽略目录，
    使用方需自行把环境变量指到 `published/current/`。

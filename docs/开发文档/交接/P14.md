## 核心口径

### 1. 四态与“不误判”

| 情形 | 证据状态 | 是否可作依据 |
|---|---|---|
| 输入为空/非数字/长度不对 | `null`（未查询） | 否，不能据此判编码无效 |
| 来源未配置/读不了/异常 | `query_failed` | 否，不等于查无此码 |
| 查到 + 版本已核 + 已复核官方 | `obtained` | 是（HS 还需 10 位且 active） |
| 查到 + 版本待核 | `version_unverified` | 否 |
| 本版本未收录 + 版本已核 | `not_found` | 否，不等于编码无效或无需要素 |
| 未收录 + 版本待核 | `version_unverified` | 否，不宣称不存在 |

格式（10 位/8 位/其它）、存在性、有效性（active/expired/merged/unknown）、版本是四个独立字段。
作废/并码只看来源声明；不按“查不到”或“本机今天”推断。

### 2. 事实充足性

`not_checked`（未核对）→ `unverified`（来源/版本/解析/条件不确定）→
`insufficient`（权威已复核版本下确有必填缺失/非法）→ `sufficient`（门槛全满足且无缺失）。

- `sufficient`/`insufficient` 只可能在“官方 + 已复核 + 版本已核 + 清单取得 + 解析确定”时出现；
- 合成/第三方/官方未复核一律 `unverified`，并在证据与问题中标注；
- 只有 `insufficient` 才生成 `supplement_items`（结果模型强制），`unverified` 不生成供应商补料；
- 条件要素未提供时一律 `unverifiable` 转专家，**不自动判断条件**；
- 位置/编号不符、名称歧义、结构化值与原文冲突，一律先人工核对原文，不猜。

### 3. 查询基准

`QueryBasis(declaration_date, tariff_version, note)` 只由调用方给出。两者为空 → 版本待核，
不填当天；日期只接受 ISO 日期/时间，解析失败不截断；日期越界或多版本重叠 → 待核；
8 位数字按税目/子目处理，不能确认 10 位申报编码。

### 4. 来源能力（2026-11-16 本机实测）

| 来源 | 结论 | 证据 |
|---|---|---|
| 海关总署「互联网+海关」税则查询 | `unreachable` | `www.customs.gov.cn` 504/超时；TLS 证书链被本机代理替换（curl self signed）；无开放 API |
| 《规范申报目录》年度版 | `requires_authorization` | 无批量下载/开放接口；本机未取得 2026 年版原件；必填口径需专家确认 |
| 单一窗口参数查询 | `requires_authorization` | GET 只返回“需要启用 JavaScript”；HEAD 403；需登录与授权 |
| 第三方 HS 站 | `available`（仅初筛） | 页面可打开；申报要素形如 `1:品牌类型;2:出口享惠情况;…`，仅用于字段形状参考 |

正式接入需 Jay/关务专家给授权导出文件，按 D6 第 2.5 节导入并复核；没有真实源时
`query_status=source_unconfigured`，绝不回退到合成样本。

## 未验证、风险与待拍板

1. **真实来源未接入（D-09）**：本包没有真实税则/规范申报目录数据；任何真实编码的
   存在性、状态、要素清单都未验证。真实导入后需逐条抽查定位与版本日期。
2. **必填/条件必填口径未定（建议新增 D-12）**：来源目录的“要素类型”不等于“必填”。
   当前 `requirement` 由数据文件声明，来源没写清就 `unknown` 并转待核；需要关务专家
   给出每个要素的必填/条件/选填口径及条件表达式。
3. **条件要素未机读化**：`condition` 只是人类可读文本，未提供时一律 `unverified`；
   这可能让真实数据中大量条件要素永远无法判 `sufficient`，需专家把条件写成规则后再评审。
4. **位置式原文可能省略尾部选填项**：数量不符一律 `partial`，不猜缺哪项；真实供应商
   原文若普遍省略尾部，需业务确认“省略即未填”还是“省略即无”，再决定是否放宽。
5. **8 位编码**：仅当来源本身收录 8 位记录时可查该记录；当前不按 10 位前缀外推层级，也不能确认 10 位要素。
6. **编码记录有效期**：真实导入必须填 `effective_from/to`；只填税则版本、不填业务申报日期，不会得到 `declaration_ready`。导入后需抽查记录有效期与公告一致。
7. **第三方字段形状参考**：仅人工查看公开页面，不抓取入库、不作为依据；若后续使用，
   必须保留来源与“待官方核验”标记。
8. **P16 集成约束**：只有 `authoritative=true` 且版本已核的结果才可当事实；其余保持
   `needs_confirmation`；`supplement_items` 只能在 `insufficient` 时使用。
9. **未做并发/性能**：纯内存/JSON 单次查询，不涉及共享状态；数据文件很大时需另评
   加载性能与缓存策略，本包不预做。

## 合并后复查（2026-11-16）

在干净 worktree 合并最新 `main@c20ab64`（含 P04）后复跑，不依赖交付时的本地状态：

- `make check` 通过、无迁移漂移；`tests.p14` 152 项全绿；`tests.p02+p15` 118 项全绿。
- A05/A08 状态矩阵复验：10 位已收录= `obtained`、未收录= `not_found`、8 位= `not_found`
  + `HS_SUBHEADING_ONLY`、12 位= `invalid_input`、缺基准= `version_unverified`、
  来源不可达= `query_failed`；均未出现“查询失败直接判无效”。
- 证据定位复验：合成记录带 `document`/`locator`/`retrieved_at`/生效日期，无记录时不生成证据。
- 权威/复核夹具逻辑复验：完整=`sufficient`、缺型号=`insufficient` + 补料、条件缺失=`unverified`、
  空要素=`insufficient`；合成来源同输入保持 `unverified` 且不生成补料。

复查发现并修复：

1. **同一要素名重复出现会被后值覆盖**（如两段“品牌类型：…”），原先仍判 `sufficient`。
   已改为 `partial`、保留首个值、转人工，并补编号式/键值式/结构化别名三组回归。
2. **编码记录有效期未参与可用性判定**：记录 `effective_from=2026-07-01`、申报日期
   `2026-05-20` 时原仍 `declaration_ready=true`。已加 `effective_status` 四态；日期早于生效、
   晚于失效、或无业务日期时一律不标可申报，并给出 `HS_RECORD_NOT_EFFECTIVE`/
   `HS_EFFECTIVE_DATE_UNKNOWN`。
3. **NFKC 归一化后超长被截断**：原串 4034 字符、含 `ﬃ`，归一化超过上限后截掉尾部冲突，
   仍可能判 `sufficient`。现改为归一化后检查长度，超限整体 `unparsed` 转人工，不截断。
4. **超长编号直接 `int()` 抛异常**：5000 位数字编号会把核对变成 500。现超过 6 位不转整数、
   按未识别处理，返回 `partial`/`unverified`。
5. **换行/空格/Tab 与混用分隔符会吞段**：`甲:正确值\n乙:另一个` 原把下一段并入上一段
   仍判 `sufficient`。现按换行/制表/“空白后跟已知要素名:冒号”切段；尾随无冒号名称不切（保留完整值），
   换行/制表后的裸名称转 `partial`；`|` 与 `;`/换行混用、值内再出现 `名称:` 冒号一律 `partial`。
6. **空白/零宽来源定位可通过**：`document=" "`、`"\u200b"`、`"\ufeff"` 能生成“可申报”结果。现 `SourceRef`
   去除不可见字符后必须非空，证据同样校验；权威证据 `retrieved_at` 必须为 ISO 时间。
7. **派生字段仍可被 `model_validate` 伪造**：`effective_status` 改为按记录日期重算；
   `sufficient` 不得带冲突/歧义/未识别/缺号；补料项的 label/role/suggested_role 必须与
   checks 一致；InMemory 存储复用 JSON 端的重复/版本/结构校验；已复核数据必须有合法
   `reviewed_at` 与 `retrieved_at`，`synthetic=true` 只能配合成来源。
8. **D4/交接对 8 位编码表述过宽**：原文写“可查层级”，实现只在来源本身收录 8 位记录时
   才可查，且不按 10 位前缀外推。已改文档，行为不变。
9. **合并流程**：PR #19 合并时没有正式 review approval，只有独立复核与本次合并后复查；
   过程上应在下次合并前补审批记录，不把“测试全绿”等同于“验收签字”。
10. **模板原文 + 完整结构化值 + 未知字段会抛异常**：解析状态停在 `template_only`，未随
    未识别字段升级为 `partial`，结果校验器因此拒绝构造。现已统一降 `partial`，返回
    `unverified` 且不生成补料。
11. **来源 `retrieved_at` 非法在结果构造期抛异常**：`2026/11/16` 能通过存储加载，
    到证据构造时才 `ValidationError`。现于 `SourceRef` 加载期校验 ISO 时间，查询返回
    `source_unreadable`/`query_failed`，不再抛 500。
12. **U+2060/U+2063 零宽字符绕过定位校验**：原过滤按枚举范围，漏了 Cf 类零宽字符。
    现按 Unicode 类别过滤 Cf/Cc/Zs/Zl/Zp 与 variation selector，空白定位一律拒绝。
13. **没有任何有效期依据时兜底成 effective**：版本待核且记录无有效期时，原实现把
    `start/end` 都为空当成“永远有效”。现返回 `unknown`，保持待核，不出现
    “版本待核 + 记录有效”的矛盾状态。
14. **Mn 类不可见字符漏过滤**：`U+034F`（组合字素连接符）与 `U+E0100`（补充变体
    选择符）可让 document/locator 通过非空校验。现按 Unicode 类别去掉 Mn/Mc/Me、
    Cf/Cc/Zs/Zl/Zp、Hangul filler 与 tag/变体补充区，再做非空判断；JSON 与内存
    两条路径都返回 `source_unreadable`/`query_failed`。

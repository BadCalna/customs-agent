### 写请求 DTO（组件当前发送的形状，2026-11-17 校正）

组件只负责操作意图，路径参数由调用方在 `api` adapter 中拼接；请求体不加路径里已有的 ID。
本节在 2026-11-15 首版写成 `expected_revision: number`、`submitted_hs`/`item_revision` 随提交发送、
退回发 `items:[{item_id, issue}]`，那是**改动前的旧形状**，与代码和契约都不符，已按现状改正。

```text
confirm({                            // PATCH /versions/{version_id}/items/{item_id}/confirmation
  confirmed_hs: string,              // 必填；不自动带入预审建议
  reason: string,                    // 修改已有确认值时必填；首次确认可空
  expected_revision: number          // ItemCard.revision，必须是整数（R-06）
})                                   // 对齐 contracts/schemas/confirmations/ConfirmationIn.json

submit({                             // POST /tasks/{task_id}/submissions
  version_id: string,
  revision: number,                  // TaskDetail.revision，必须是整数（字段名就是 revision）
  items: [{ item_id: string, confirmation_id: string }]
})                                   // 对齐 contracts/schemas/submissions/SubmissionIn.json
                                     // 不发送 submitted_hs / item_revision：值由服务端按确认记录取

decide({                             // POST /submissions/{submission_id}/decisions
  action: "approve" | "return",
  reason: string,                    // 通过时可空；退回时必填
  return_to?: "supplier" | "operator",   // 仅退回
  items?:   [{ item_id, final_hs, change_reason }],   // 仅通过；未改行也进 items，change_reason=""
  issues?:  [{ item_id, message }]                    // 仅退回；至少一条
})                                   // 对齐 contracts/schemas/decisions/DecisionIn.json
                                     // 不发送 previous_hs / expected_revision：前值由服务端从提交快照取
```

提交前拦截规则：

- 任一商品 `business_confirmed_hs.value` 或 `.source_id` 为空 → 整批提交按钮禁用，并列出缺确认行；
- 明确提示不会用预审建议、供应商原码、专家建议、旧提交或空值补位；
- **修订号按原始值校验（R-06）**：任务修订号（`TaskDetail.revision`）、逐行商品修订号
  （`ItemCard.revision`）、提交修订号（`Submission.revision`）都要求“存在且是整数”才发送；
  `null`、空串/空白串、字段缺失、小数、非数字字符串、布尔一律拦截，不做 `Number()` 隐式转换
  （旧实现在 `null`/`""` 时会变成 `0` 并照常发请求）；
- 版本 ID 缺失时不发送请求。

专家通过的逐行规则：

- 提交值只读展示；终值输入留空即等于提交值；
- 终值 ≠ 提交值时改码原因必填，`items[].change_reason` 填原因；`previous_hs` 由服务端按提交快照留痕，不由前端发；
- 未改行也进入 `items`（`final_hs=提交值`、`change_reason=""`），不省略成“部分通过”；
- 退回必须二选一对象、填写原因，并至少一条逐商品问题。

在飞请求与草稿（R-05，本轮定下的策略）：

- 请求 pending 时输入框仍可编辑（不禁用）；成功后**只清理仍等于提交时快照的字段**，
  请求期间的新输入保留；失败一律保留全部草稿。
- 清理还绑定提交时的作用域（2026-11-17 补）：确认用「任务+版本」两段键，决定用「任务+版本+提交」
  三段键。请求在飞时若用户切到另一份提交（或另一个任务/版本），响应回来**不清理**当前作用域的草稿，
  反馈改成「…已返回，但当前视图已切换到另一份作用域」，不把别人的成功结果显示成当前视图的结果。
  边界说明：同一份提交/版本内的新输入一定保留；跨作用域时保留的是**新作用域自己的草稿**，
  旧作用域的草稿留在它自己那一档（切回旧作用域仍能看到），不会串档、也不会被旧响应清掉。
- 选“按字段比较”而不是“禁用输入”的理由：用户在等待期间仍要核对/记录，禁用会让输入直接丢失；
  按字段比较既能清掉已提交内容，又能保证新输入不被较早的响应抹掉。两种做法都在审核建议范围内，这里选了前者。

### 错误与冲突交互

| 响应 | 组件行为 | 草稿 |
|---|---|---|
| 501 `not_implemented` | 标题「未实现（501）」，显示 `error.message` 与 `details.owner`；不显示业务结论 | 保留 |
| 409 `conflict` | 标题「内容已被他人修改，已刷新」；调用 `onConflict`（或 `onRefresh`）由调用方重新拉取。**刷新回调抛错时**标题改为「内容已被他人修改，请刷新后重试」并列出「自动刷新未完成：<原因>」；页面侧 `conflictRefresh` 必须继续抛出（已抽成 `web/pages/p11-conflict.js` 的 `createConflictRefresh`，行为由 Node 用例驱动，见二轮修复记录） | 保留 |
| 403 `forbidden` | 「没有该动作的权限（403）」，说明 `allowed_actions` 只做展示 | 保留 |
| 403 `csrf_failed` | 「CSRF 校验失败（403）」，提示重新登录 | 保留 |
| 401 `unauthorized` | 「登录已失效（401）」 | 保留 |
| 404 | 「对象不存在或不可见（404）」 | 保留 |
| 400/422 | 「请求未通过校验（400/422）」，显示 `details.fields`（若有） | 保留 |
| HTTP 2xx | 「服务端已响应」，只显示响应中的 `status`/`revision`/`submission_id`；不写“成功/通过” | 仅此时清理，且**只清理仍等于提交时快照的字段**（R-05）；请求期间的新输入保留。若响应回来时作用域已切换，则一个字段都不清，并提示「已切换到另一份作用域」 |
| 网络异常 | 「请求失败」，不推断业务结果 | 保留 |

所有失败路径都在 `finally` 恢复 `state.pending = ""`，按钮重新可用；请求期间按钮 `aria-busy=true` 并显示「处理中… / 提交中…」。

### 版本历史视图模型（P11 建议，尚未进入契约）

**2026-11-17 校订**：`GET /tasks/{task_id}/history` 与 `contracts/schemas/history/TaskHistoryOut.json` 现在都已存在（P10 交付）。
这段视图模型是 2026-11-15 P11 自拟的（自测页按它装配数据），与已发布 schema 有差异（见申请 A/B），**不是契约**；
组件当前只保证「按这个视图模型给数据能正确渲染」，尚未按正式 schema 适配。

```text
{
  task_id, current_version_id,
  versions: [{
    version_id, number, original_filename, uploaded_at, is_current, approved?,
    submissions: [{
      submission_id, revision, status, created_at, created_by,
      expert_check?: { target_hs, status, run_id },
      items: [{ item_id, name, source_location, submitted_hs, item_revision }],
      decisions: [{
        decision_id, action, return_to, reason, created_at, created_by,
        expert_check?: { target_hs, status, run_id },
        // 通过：逐行终值；退回：逐商品问题（二选一，见“契约变更申请 A”）
        items: [{ item_id, name, source_location, previous_hs, final_hs, change_reason, issue? }]
        issues?: [{ item_id, message }]   // 接受决定级问题；同一 item 的多条用「；」累加，不丢第 2..n 条
      }]
    }],
    decisions?: [...]   // 也接受版本级决定，按 submission_id 归并；无匹配时原样展示为“未关联”
  }],
  candidates?: [{
    basis,
    left:  { version_number, row_number, name, hs },
    right: { version_number, row_number, name, hs }
  }]
}
```

守卫规则（2026-11-17 二次修正，含任务级快照的 P1 回归）：

- 判定只用当前视图状态（`taskId` / `activeVersionId`）；`accept(data, scope)` 的 scope 只是调用方自证，
  与视图不一致时直接丢弃，用来挡住晚到的旧请求；
- 版本作用域数据必须带 `version_id` 且等于 `activeVersionId`；不同则拒绝，保留上一份已接受的数据；
- 任务级数据（带 `versions[]` 且不带 `version_id`）先校验 `task_id`，再要求 `versions[]` 里**存在**
  `activeVersionId`：正在看 V2 时，一份只含 V1 的过期快照（`current_version_id="v1"`）会被丢弃，
  不会把视图换成 V1。但这不等于要求 `current_version_id == activeVersionId`——看旧 V1、任务当前 V2、
  响应里两版都有时照常接受（旧实现要求相等，会把正常场景误拒）；`current_version_id` 只用于标记当前/旧版本；
- 构造参数 `data` 先进 `pendingData`，`mount()` 里同样走 `accept()` 判定：被拒绝的首次数据不渲染，
  `getState().hasData` 保持 `false`，页面不会出现「已丢弃」提示与被丢弃内容同时显示；
- 拒绝时显示「已丢弃版本不匹配的历史响应」、响应/当前版本标签（V1/V2）与具体原因（版本级写 `version_id`
  不匹配，任务级写「任务级快照不含当前视图版本」并列出响应里的版本集合）；
- 修复后成立的说法：**晚到 V1 响应会被丢弃、当前 V2 视图保持**——版本级由「M-08b」「FIX-09 主校验」
  用例锁住，任务级由「P1 回归 看 V2 时晚到的『只有 V1』任务级快照必须丢弃」锁住；
  「M-08c」用例反向锁住「不得要求正在查看的版本等于任务当前版本」。

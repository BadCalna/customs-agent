### 写请求 DTO（组件当前发送的形状）

组件只负责操作意图，路径参数由调用方在 `api` adapter 中拼接；请求体不加路径里已有的 ID。

```text
confirm({
  confirmed_hs: string,          // 必填；不自动带入预审建议
  reason: string,                // 修改已有确认值时必填；首次确认可空
  expected_revision: number      // ItemCard.revision
})

submit({
  version_id: string,
  expected_revision: number,     // TaskDetail.revision
  items: [{
    item_id: string,
    submitted_hs: string,        // 只取 business_confirmed_hs.value
    confirmation_id: string,     // 只取 business_confirmed_hs.source_id
    item_revision: number
  }]
})

decide({
  action: "approve" | "return",
  expected_revision: number,     // Submission.revision
  reason: string,                // 通过时可空；退回时必填
  return_to?: "supplier" | "operator",  // 仅退回
  items: approve
    ? [{ item_id, previous_hs, final_hs, change_reason }]
    : [{ item_id, issue }]
})
```

提交前拦截规则：

- 任一商品 `business_confirmed_hs.value` 或 `.source_id` 为空 → 整批提交按钮禁用，并列出缺确认行；
- 明确提示不会用预审建议、供应商原码、专家建议、旧提交或空值补位；
- `TaskDetail.revision` 不是整数时不发送请求；版本 ID 缺失时不发送请求。

专家通过的逐行规则：

- 提交值只读展示；终值输入留空即等于提交值；
- 终值 ≠ 提交值时改码原因必填，并发送 `previous_hs=提交值`、`change_reason`；
- 未改行也进入 `items`，`previous_hs=final_hs=提交值`、`change_reason=""`，不省略成“部分通过”；
- 退回必须二选一对象、填写原因，并至少一条逐商品问题。

### 错误与冲突交互

| 响应 | 组件行为 | 草稿 |
|---|---|---|
| 501 `not_implemented` | 标题「未实现（501）」，显示 `error.message` 与 `details.owner`；不显示业务结论 | 保留 |
| 409 `conflict` | 标题「内容已被他人修改，已刷新」；调用 `onConflict`（或 `onRefresh`），由调用方重新拉取；刷新失败时改为「自动刷新失败，请手动刷新」 | 保留 |
| 403 `forbidden` | 「没有该动作的权限（403）」，说明 `allowed_actions` 只做展示 | 保留 |
| 403 `csrf_failed` | 「CSRF 校验失败（403）」，提示重新登录 | 保留 |
| 401 `unauthorized` | 「登录已失效（401）」 | 保留 |
| 404 | 「对象不存在或不可见（404）」 | 保留 |
| 400/422 | 「请求未通过校验（400/422）」，显示 `details.fields`（若有） | 保留 |
| HTTP 2xx | 「服务端已响应」，只显示响应中的 `status`/`revision`/`submission_id`；不写“成功/通过” | 仅此时清除对应草稿 |
| 网络异常 | 「请求失败」，不推断业务结果 | 保留 |

所有失败路径都在 `finally` 恢复 `state.pending = ""`，按钮重新可用；请求期间按钮 `aria-busy=true` 并显示「处理中… / 提交中…」。

### 主控/后续页面挂载方式

组件不读 cookie、不发请求、不引入框架。调用方传入 `api` 与视图数据：

```js
import { createReviewActions } from "/demo/assets/components/review-actions.js";
import { createVersionHistory } from "/demo/assets/components/version-history.js";

const actions = createReviewActions({
  api: {
    confirm: (payload) => write("PATCH", confirmationPath, payload),
    submit: (payload) => write("POST", submissionPath, payload),
    decide: (payload) => write("POST", decisionPath, payload),
  },
  role: "operator",              // 或 "expert"
  data: { task, version, items, submission, expert_check },
  onConflict: async () => reloadAll(),   // 409 后重新拉取
  onChanged: async () => reloadAll(),    // 2xx 后由调用方取权威状态
});
actions.mount(document.querySelector("#review"));
actions.update(nextData);        // 保留未提交草稿

const history = createVersionHistory({
  data: historyPayload,
  taskId: task.task_id,
  activeVersionId: currentVersion.version_id,
  currentVersionId: currentVersion.version_id,
  activeVersionLabel: `V${currentVersion.number}`,
  currentVersionLabel: `V${currentVersion.number}`,
});
history.mount(document.querySelector("#history"));
const accepted = history.accept(lateResponse, { taskId, versionId: currentVersion.version_id });
// accepted === false 表示版本不匹配、已丢弃，当前视图不被覆盖
```

`web/api.js` 目前只有只读方法，P11 不允许修改它。需要主控在 P09/P10 接线时给 live/fixture adapter 增加同名的 `confirm`/`submit`/`decide`，或在页面层传入 adapter；组件无需改动。**这是本包对公共文件的唯一申请，未自行修改。**

### 版本历史视图模型（P11 建议，尚未进入契约）

`GET /tasks/{task_id}/history`（P10）尚未实现，`contracts/schemas/` 也没有历史 schema。组件按下列视图模型渲染，字段名尽量复用契约已有命名；P10 发布正式 schema 后应以正式字段为准，组件再做适配。

```text
{
  task_id, current_version_id,
  versions: [{
    version_id, number, original_filename, uploaded_at, is_current, approved?,
    submissions: [{
      submission_id, revision, status, created_at, created_by,
      expert_check?: { target_hs, status, run_id },
      items: [{ item_id, name, source_location, submitted_hs, item_revision }],
      decisions: [{
        decision_id, action, return_to, reason, created_at, created_by,
        expert_check?: { target_hs, status, run_id },
        items: [{ item_id, name, source_location, previous_hs, final_hs, change_reason }]
      }]
    }],
    decisions?: [...]   // 也接受版本级决定，按 submission_id 归并；无匹配时原样展示为“未关联”
  }],
  candidates?: [{
    basis,
    left:  { version_number, row_number, name, hs },
    right: { version_number, row_number, name, hs }
  }]
}
```

守卫规则：

- 版本作用域数据必须带 `version_id`；与 `activeVersionId` 不同则拒绝，保留上一份已接受的数据；
- 任务级数据（带 `versions[]`）按 `task_id` 校验；版本分组各自标记当前/旧版本；
- 拒绝时显示「已丢弃版本不匹配的历史响应」和响应/当前版本标签（V1/V2），不用 V1 覆盖 V2。

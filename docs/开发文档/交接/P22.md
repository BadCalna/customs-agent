## 关键设计决定

1. **部署开关不进公共配置**。`config/settings.py` 里 `DEBUG=True`、`ALLOWED_HOSTS` 是硬编码开发值，
   但那是主控维护、P06 可能在改的文件。P22 另建 `deploy/settings_cloud.py`：
   `from config.settings import *` 后只覆盖部署项，用 `DJANGO_SETTINGS_MODULE` 切换。
   开发机行为一字未变，也不会和 P06 抢同一个文件。
2. **ALLOWED_HOSTS 故意不给默认值**。缺失即 `ImproperlyConfigured`：宁可起不来，也不要悄悄接受任意 Host。
   同理 `CUSTOMS_CSRF_TRUSTED_ORIGINS` 每项必须带协议，写错就启动失败而不是运行时 403 排查半天。
3. **Secure cookie 只在显式 `CUSTOMS_HTTPS=1` 时开启**。纯 HTTP 测试开 Secure 会表现为
   “登录成功但立刻变匿名”，这是新手最容易卡住的一类问题。
4. **静态资源交给 nginx，不引入新 Python 依赖**。`DEBUG=0` 后 Django 不再服务 `/static/`；
   用 `collectstatic` 写入 `static` 卷 + nginx `alias` 解决，避免为了 whitenoise 去改 `uv.lock`（公共依赖锁）。
5. **gunicorn 走镜像内安装而非加进 `pyproject.toml`**。运行器是部署细节，不该改公共依赖清单；
   镜像里 `uv pip install gunicorn==23.0.0` 固定版本，可复现。
6. **迁移与 collectstatic 用一次性 `migrate` 服务**，`app` 以 `service_completed_successfully` 依赖它。
   多副本同时迁移是经典的启动竞态，这里用编排顺序规避，不靠应用内重试。
7. **数据库不发布端口**，只 `expose`；外部唯一入口是 nginx。安全组只需开一个测试端口。
8. **文件卷挂在 `/srv/customs` 而不是 `/srv/customs/files`**。这样“恢复到独立目录”“回退到旧文件目录”
   都落在同一个卷内的兄弟目录，不必移动原件；回退只需改 `CUSTOMS_FILE_ROOT`。
9. **备份默认先停写**。数据库与文件是两套存储，不停写就无法声称同一时点；脚本头部与 D6 都写明
   `--no-quiesce` 的边界，不允许把不同时点快照说成一致。
10. **恢复只进隔离目标，且目标存在即拒绝**。P12 的教训（`pg_restore --no-owner` 归属错、直接覆盖难回退）
    决定这里不做原地覆盖；回退用“换指向”新库/新目录的方式，原数据全程保留。
11. **备份排除 `incoming/`**。那是“已落暂存、事务未提交”的半成品（P05 设计），备份它反而是脏数据。
12. **redis/worker 保留位但默认不启动，并显式写“P13 未实现”**。`CUSTOMS_EXECUTOR_MODE` 目前只接受
    `inline`，即使启用队列也不会有任务被处理——这点写进 compose 注释、README 与 D6，避免误解。
13. **部署镜像 Python 固定 3.13**（dev 是 3.14）。`uv.lock` 通用，3.13 的 psycopg/Pillow 轮子最齐，
    构建不需要编译工具链；`requires-python` 范围同时覆盖两者。

## 备份/恢复一致性边界（复核口径）

- 默认停写 → 数据库与文件同一时点；停写期间服务不可用，时长取决于文件体积。
- `--no-quiesce` → 两个相邻时点，可能出现“库引用未落盘文件”，**不得**当正式备份。
- 备份只读：不删库、不删文件；`backup.sh` 里没有任何 `dropdb`/`rm -rf`（有测试锁住）。
- 恢复拒绝覆盖既有库/目录；`django_session` 不参与比对（易变，比较它会制造假告警）。
- 不做降级迁移；数据回退走“恢复出新库 + 改 `CUSTOMS_PG_NAME`/`CUSTOMS_FILE_ROOT` + 只重启 app/web”。

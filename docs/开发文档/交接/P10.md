## 关键设计决定

1. **退回不产生终值**。`return` 决定只写 `Decision(action, return_to, reason)` 与 `Issue`，不写 `DecisionItem`；
   传了 `items` 直接 422，避免"退回却给了终值"的脏数据。通过则必须覆盖快照全部商品（R09）。
2. **旧提交在新版本出现后不可处置**（`stale_submission` 409）。这是 B08"旧版本通过不授予新版本"的服务端兜底，
   而不是靠前端隐藏按钮。
3. **业务员退回走 Issue，不伪装成专家决定**。`Decision` 必须挂在提交上，业务员退回没有提交对象，
   因此只落 `Issue(kind=operator_return)` + 审计 + 阶段；有待审提交时拦截（`submission_pending`），
   不允许"提交在审、任务又被退回"的双轨。
4. **退回权限沿用 `submission.create`**。D3 角色矩阵没有单列"退回"动作，本包按"业务员对任务的处置"处理，
   已写入 D3 第 9 节待 Jay 确认；若要单列动作，需要改 `accounts.permissions` 与 `allowed_actions` 枚举（主控变更）。
5. **历史只读、不推断身份**。`GET /tasks/{id}/history` 返回版本→提交→决定/执行、确认全修订、问题、审计事件（最多 100 条）；
   `cross_version_candidates` 只按合同号+项号、品名给候选，响应里明确写"不代表同一商品身份、旧结论不沿用"。
6. **幂等与 P09 同一套**。决定/退回复用 `services/idempotency.py`，同 key 重放首次决定，同 key 不同内容 409；
   已处置提交再次决定 409 `submission_closed`。

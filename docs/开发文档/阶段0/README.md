## 怎样一起写最省事

正文以这组 Markdown 文件为准，聊天和批注用于提出修改。每轮围绕一个主题，例如任务粒度、商品对应或专家退回；修改后继续维护同一份正文。

约定四类标记：

- **已确认**：Jay 在当前会话明确决定的业务规则。
- **流程基线**：当前流程图及现行说明已有的规则，列明出处。
- **建议**：Agent 提供的可修改方案，尚未升级为确认规则。
- **待定**：仍需业务决定，或需真实模板验证。

你可以在聊天里按编号批注，也可以直接在段落下写：

```text
R02：确认。
Q03：补料重传保留同一个任务，只增加文件版本。
S02：供应商通常会重新复制整张表，请把这个情况补进去。
```

直接编辑文件时，批注可以写成：

```text
> Jay（Q02）：补料文件不携带系统 ID，重传后整表重新预审。
> 同事A（S03）：这里实际应该先退回业务员，再由业务员联系供应商。
```

Agent 每轮负责：读取当前正文和新批注，保留用户原意，修改相关段落，检查关联规则与例子，并简要说明改了什么、还剩什么。明确决定同步到 R 规则和决定记录；建议与问题保持原状态，不能因重复出现就自动视为确认。已解决批注归入决定记录后再从正文清理。

Jay 负责业务目标、范围和流程取舍；关务专家核验专业判断和真实案例答案；开发或 Agent 将规则转成字段、接口和可验证的实现。文字修正、同步已决定事项和补充说明可直接推进。

## 其他同事怎么协作

建议每人或每个工作主题用独立分支，完成一小组修改后发起 PR（合并请求），由协作者看修改差异、逐段评论，再合并。GitHub 支持对修改行评论和提交具体替换建议，适合文档共写。

同一个工作区里先约定谁编辑哪个文件；不同 Agent 或编辑器操作同一文件前都重新读取最新内容。一个主题优先由一个人整合正文，其余人提供批注，减少相互覆盖。

推荐每轮形成一组可说明的改动，例如“明确补料版本规则”，再作为一个小提交保存；提交时只包含本轮明确文件，避免夹带其他人的暂存内容。分支名、PR 和提交属于后续协作操作，本次草拟没有创建或推送它们。

官方参考：[GitHub PR 审阅与修改建议](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request)。

## 进入阶段 1 的标准

- [ ] 基本任务、角色、HS 确认和退回流程没有未解释的冲突。
- [ ] 取得一份真实脱敏模板，核对相关页签、字段、图片和已有意见。
- [ ] 明确商品行粒度（申报要素页签维度）与补料重传后的展示对照办法；对不上时有人工处理。
- [ ] 三个样例完成桌面走查，补上实际业务差异，留下结论。
- [ ] 解析与导出所需的关键问题已有决定或明确处理路径；非阻断问题可继续保留。

这些是阶段 0 的目标，当前初稿未将它们标记为通过。后续详细接口、数据库类型和完整测试在对应开发阶段补充。

# Agent 协作与交接约定

版本：1.0，2026-11-13。适用于编程 Agent；系统内关务 AI 的输出规范另见 [D4](Agent输入输出与证据约定.md)。

## 1. 派发前必须具备什么

主控只把边界清楚的任务交给执行 Agent。每包按 [任务包目录](Agent任务包.md) 补齐以下内容，保存在 `docs/开发文档/交接/Pxx.md`；没有就标“未具备”，不能让执行 Agent 猜测。

| 内容 | 最小要求 |
|---|---|
| 代码基线 | 仓库绝对路径、分支/工作目录、基线 commit；列出已有未提交修改，不混入本任务 |
| 依赖 | 编码依赖已完成可供下游使用的模块自验和契约发布，不要求该依赖的最终集成也已结束；集成依赖未满足的逐项列出，允许先用指定 mock |
| 契约 | D1 规则编号、D2/D3/D4 对应章节、schema 版本；以基线中的实际文件为准 |
| 输入 | 样例路径、场景 ID、预期输出；真实样本仅本地，脱敏样例可入库 |
| 文件范围 | 明确到目录或文件；公共模型、迁移、schema、锁文件和全局路由默认归主控 |
| 执行入口 | 提供可复制的开工指令、必读文件、环境初始化命令和第一条可执行检查；注明样例是否只在本机可用 |
| 验证入口 | 在基线能运行的命令和预期成功条件；尚未实现的命令必须由前置任务先补齐 |
| 回交 | 代码差异/commit、测试证据、文档变更、限制、下一步接续办法 |
| 手工测试 | 给 Jay 可操作的步骤、页面地址或文件路径、预期结果和必要测试账号的准备方法；实际结果由 Jay 测试后记录 |

任务表里的目标路径和命令是交付约定。P00/P02 必须实际建立这些入口；基线缺文件时执行 Agent 返回缺失项，不能声称按不存在的命令通过。

## 2. 分支与文件所有权

- 每个任务包使用一个 feature 分支，例如 `feature/P01-models-permissions`、`feature/P03-excel-fidelity`。从主控指定的已提交基线创建，回交后由主控审查并合入 main。
- 多个 Agent 在同一台电脑同时开发时，每个任务使用独立 Git worktree（同一仓库对应的独立工作目录）；分别在自己的目录中切换分支。不同电脑可以各自在自己的 clone 中创建分支。运行数据库、上传和导出目录各自独立，worktree 中所需真实样本另行准备。
- 主控记录“谁正在改哪些文件”。任务包中较宽的目录范围只是上限，派发时收窄到具体文件；重叠任务串行或拆文件。
- 公共模型、迁移、认证策略、状态枚举、契约、依赖版本、`web/api.js` 和入口路由由主控统一写入。需要修改时执行 Agent 在回交记录中提出具体字段/理由/影响，主控更新契约后再继续依赖它的代码。
- 同一个 Django app 的迁移按集成分支顺序产生；不能把不同 Agent 的同号迁移直接拼接。已经部署的迁移通过追加迁移修正，不重写历史。
- 执行 Agent 不整体重构原型、不更换技术栈、不引入第二套账号或状态、不顺手修改任务外文件。发现任务外缺陷时记录位置与影响。
- 主控集成前重新读取目标分支和差异，只接入该任务的文件；合并后在集成分支重新运行受影响检查。仓库推送、上线和真实消息发送按用户实际授权执行，不由“模块已完成”隐式触发。

## 3. 契约怎样发布和变更

P02 将 D3/D4 转为可校验的 schema、固定样例和 API 文档，发布契约 v1。文档和示例同时更新，不能只改其中一个。执行 Agent 读取已发布的固定版本进行开发。

变更申请必须包含：旧字段/行为、新字段/行为、原因、受影响任务、是否兼容、需要补的样例和迁移。主控维护唯一版本；影响旧消费者时先补兼容或集中升级，再放开依赖任务。未知字段和值不应在前端私自转换成成功、通过或无问题。

前端只提交操作意图，后端校验权限和业务状态；mock 和真实实现通过同一 schema。业务状态、执行状态、证据状态、比较结论、人工决定分别建模。

## 4. 执行过程与阻塞处理

执行 Agent 开始先读本任务包及指定 D 文档；仓库内有 `AGENTS.md` 时一并读取。核对基线、可写范围和样例是否存在，再按派工单完成实现、必要测试和文档。初始化及通用命令以 [D6](运行与交接说明.md) 为准，技术问题由执行 Agent 诊断并向主控回交具体结果。

出现以下情况时停止依赖该项的代码，写明“缺什么、影响哪个验收、已验证什么、谁接手”，可继续独立工作：业务规则冲突、接口真实能力不明、前置任务未发布、样本缺失、权限限制或需要改公共契约。不能用编造数据或弱化验收标准抹掉阻塞。连续两轮针对同一失败尝试仍无进展时，回交诊断及可复现输入，由主控调整任务边界。

这条停止规则只针对有依赖的部分，不要求每个实现细节都询问 Jay。代码命名、局部算法、样式等在既定范围内由 Agent 自主完成。

## 5. 回交文档模板

每包必须交 `docs/开发文档/交接/Pxx.md`，保留以下段落，不用“全部完成”替代事实。

```markdown
# Pxx 任务名称

## 派发基线
- 目标、范围及不包含项：
- 仓库绝对路径、分支/工作目录、基线 commit：
- D1 规则编号、D2/D3/D4 与 schema 版本：
- 已具备的编码依赖、未具备的集成依赖：
- 样例路径及场景 ID：
- 开工指令、环境初始化与首次检查命令：
- 允许修改的文件、主控保留文件：
- 验证命令与预期：

## 回交内容
- 提交 commit 或明确文件差异清单：
- 逐项交付物及路径：
- 启动/调用方式与输入输出示例：
- 实际运行命令、退出码、时间、数据库/引擎/执行器模式：
- 证据路径、实际观察与验收结论：
- 未执行的检查及原因：
- 新增配置、依赖、迁移或数据兼容影响：
- 契约变更申请、未解决问题及接手人：
- 后续 Agent 从哪一步继续：

## Jay 手工测试
- 启动方法与必要账号准备：
- 逐步操作、页面地址或待检查文件、预期结果：
- 实际结果与问题记录：待 Jay 测试后填写。

## 主控验收
- 差异审查结论：
- 集成基线 commit：
- 集成验证命令与实际结果：
- 业务/专业验收状态：
- 状态：待开始 / 进行中 / 模块待验收 / 集成待验收 / 已验收 / 阻塞
```

真实表、账号、密钥、完整请求日志不能随交接文档提交。记录脱敏样本标识和必要摘要；大文件产物留本地并记录位置、哈希及复现方法。

## 6. 完成的判定

| 状态 | 需要的证据 |
|---|---|
| 模块自验通过 | 目标文件内实现完成，约定输入输出与异常场景有实测记录，未执行项目明确列出 |
| 集成验收通过 | 接入公共入口后可调用；服务端、页面、真实数据库或文件结果与契约一致；没有任务外改动和重复定义 |
| 业务验收通过 | Jay/关务专家按约定样例确认流程及专业结论；AI 自评只作辅助 |

任务包是否“已验收”按该包规定的门槛决定，记录适用环境。P07 的 fixture 页面通过仅代表组件通过，不能证明权限或真实 API 正确；SQLite 通过不能证明 PostgreSQL 并发正确；mock 引擎通过不能证明归类质量。

Agent 自验完成后提供上述手工测试步骤，单独记录 Jay 的实际结果。当前 P00 技术自验通过，Jay 手工测试待进行，P01 可基于已可运行的工程继续开发。

权限、快照、过期回写、重复执行、文件保真等关键包交给独立验收 Agent 复核。若暂时只有一个 Agent，会话中单独进行验收步骤并保留证据，不宣称做过独立审查。

## 7. 主控派发提示词

```text
执行 docs/开发文档/Agent任务包.md 中的 Pxx。
以交接/Pxx.md 的派发基线为准，先读指定 D 文档；仓库内有 AGENTS.md 时一并读取。
先执行派工单中的环境与样例检查，再完成实现、验证和回交。
完成范围内的实现、必要验证和回交记录；不修改主控保留文件。
需要公共契约变更时提交明确申请；前置缺失时报告阻塞并继续独立部分。
不得将 fixture/mock 的成功写成真实接口或真实 AI 已验收。
回交代码差异、真实检查结果、未解决问题及接续步骤。
```

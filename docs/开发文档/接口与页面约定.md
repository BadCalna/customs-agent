## 1. 共有约定

- API 前缀 `/api/v1`，统一走 Django Ninja。页面从同一服务访问，采用 Django session 身份和写请求 CSRF 校验；具体未登录响应由 P01 统一定义为 JSON，不返回页面重定向给 API 调用者。
- ID 按不透明字符串传递。HS 原文按字符串保存，保留空白和异常原值；未生成的阶段值为 `null`，不自动用别的阶段补位。
- 请求需携带所属版本；人工修改携带 `expected_revision`。服务端同时验证 task、version、item、submission 的关系及角色权限，不能仅按某个 ID 查询就写入。
- 创建版本、提交、审核决定、重跑/重试等写操作使用 `Idempotency-Key`。同一操作者、动作、对象和相同请求重试返回同一操作结果；同 key 不同内容返回 409。数据库唯一约束与事务实现，不能只在进程内缓存去重。
- 返回时间用带时区的 ISO 8601；分页结果 `{items, next_cursor}`；文件/图片 URL 为需要权限校验的下载路由或受控短期链接，不暴露服务器绝对路径。
- 成功结果按具体 schema 返回；错误统一 `{error: {code, message, details}, request_id}`。400 格式错误，401 未登录，403 动作不允许，404 对象不存在或不在可见范围，409 版本/修订/状态冲突，422 语义校验失败；实际框架响应由 P02 适配并测试。
- `allowed_actions` 只帮助页面展示；每次服务端仍重新校验。GET 查询无副作用，不因查询进度推进模拟执行或创建任务。

## 2. 端点及职责

下表为待实现契约；P02 按里程碑暴露端点，尚未实现的动作显式返回未实现错误，不能伪造成功。模型模拟和界面 fixture 使用同一组正式端点/schema。

| 方法与路径 | 角色 / 输入 | 输出与副作用 | 实现任务 |
|---|---|---|---|
| `POST /auth/login`、`POST /auth/logout`、`GET /me` | 账号凭据/当前会话 | 登录状态、当前角色；登录也执行相应 CSRF 防护 | P01 |
| `GET /tasks` | 已登录；阶段/分页 | 当前用户有权访问的任务列表 | P02/P06 |
| `POST /tasks` | 供应商；multipart 文件和必要归属信息 | 新任务、V1、解析执行 ID；首次上传事务失败不留半个有效任务 | P06 |
| `GET /tasks/{task_id}` | 对象读取权限 | 当前版本、业务阶段、允许动作、最新执行引用 | P02/P06 |
| `POST /tasks/{task_id}/versions` | 供应商；文件、`expected_current_version_id` | 原任务新增版本，原件不覆盖；重复请求不重复创建 | P06 |
| `GET /versions/{version_id}/items` | 版本读取权限；分页 | 商品列表、位置、原值和关键阶段结果引用 | P02/P06 |
| `GET /versions/{version_id}/items/{item_id}` | 版本/商品读取权限 | 完整卡片、图片状态、问题和结果集引用 | P02/P06 |
| `GET /runs/{run_id}` | 所属任务读取权限 | 执行范围、逐行状态、进度、错误、是否当前有效执行 | P02/P13 |
| `POST /versions/{version_id}/prechecks` | 获准重新预审的业务员 | 创建新执行，保留旧结果；自动预审由服务器事件触发 | P13 |
| `POST /runs/{run_id}/retries` | 获准重试的角色；失败 item IDs | 新尝试/子执行引用，保留旧失败；成功行不重写 | P13 |

| `POST /tasks/{task_id}/returns` | 业务员；version、revision、供应商及逐商品问题 | 退回记录；不自动导出/发送附件 | P10 |
| `POST /submissions/{submission_id}/decisions` | 专家；approve/return、revision、逐行终值/改码原因或退回对象/问题 | 人工决定和审计；整批批准，拒绝失效提交 | P10 |
| `GET /tasks/{task_id}/history` | 任务读取权限 | 按版本/提交/执行划分的只读历史，不推断跨版本同一商品 | P10/P11 |

| `GET /files/{file_id}` | 文件所属任务与版本权限 | 原文件、图片或导出文件下载 | P05/P06/P20 |
| `GET /messages`、`PATCH /messages/{message_id}` | 本人消息；已读状态 | 消息列表/已读状态；他人消息不可访问 | P19 |

## 3. 卡片最小字段

P02 将下面的字段组落实为 schema，并提供完整可验证样例；前端只在这些字段上渲染，不能从显示文案反推状态。

| 字段组 | 约定 |
|---|---|
| 身份 | `task_id, version_id, item_id, revision` |
| 源位置 | `source_location = {sheet_name, row_number, cells}`；行号为 Excel 的 1 起始编号 |
| 事实 | `name, attributes, supplier_hs_raw, supplier_elements_raw, supplier_tax_rate_raw`；原文和结构化提取分开 |
| 图片 | `images` 和 `image_status`，至少区分 available/absent/read_failed；错误包含源单元格 |
| 编码阶段 | `precheck_suggested_hs, business_confirmed_hs, submitted_hs, expert_suggested_hs, expert_final_hs`；每项带所属 run/submission/decision 引用 |
| 结果 | `comparison_status, issues, evidence_status, confidence, latest_run_id, result_mode`；业务含义见 D4 |
| 页面行为 | `allowed_actions`、当前任务/提交状态；状态由服务端汇总 |

执行进度至少包含 `total, queued, running, succeeded, failed` 和执行状态。各计数指该执行中不同商品的当前状态，总数应一致；重试次数另计。等待补充事实是业务结论，不能加进技术 failed 数。

## 4. 模拟场景与替换要求

| 场景 ID | 必须呈现的行为 |
|---|---|
| FIX-01 正常建议 | 原值、建议、来源状态可见；显示 mock 标记，不自动审批 |
| FIX-02 缺关键事实 | 执行成功，业务待确认，问题具体；建议可为 null |
| FIX-03 图片失败 | `read_failed` 与无图片不同，能看到原始位置 |

| FIX-06 查询失败 | 未取得证据及原因明确，不生成“已核实”或高置信结论 |

| FIX-09 V1 延迟返回 | 当前 V2 页面不被 V1 响应覆盖，V1 在历史中仍可见 |
| FIX-10 专家改码 | 原提交码、专家终值、改码原因分别展示，旧核查所针对 HS 明确 |

两种 mock 不混用：

1. 组件 fixture：读取固定 JSON，只用于开发组件和状态展示，无持久化/权限保证。
2. 集成 mock：真实 Django API、ORM、身份、快照、日志、执行记录，替换的只是外部 AI/查询响应。刷新页面或重启服务仍能读到结果。

`web/api.js` 集中处理 CSRF、请求、错误、幂等键、分页和模式选择。切换任务/版本时取消旧请求或检查响应身份；不能将晚到的旧响应填入当前卡片。fixture 和 live adapter 公开同样的方法，业务代码不散布 mock 条件。

## 6. 身份、会话与权限语义（P01 发布，2026-11-14）

P01 落地的内容：`POST /api/v1/auth/login`、`POST /api/v1/auth/logout`、`GET /api/v1/me`，以及服务层对象权限 `apps/accounts/permissions.py`。业务读写端点由 P02 起实现，但必须复用本节的错误语义与权限服务，不得另写一套。

### 6.1 未登录、不可见与不允许

| 情形 | HTTP | `error.code` | 说明 |
|---|---|---|---|
| 未登录 / 会话失效 | 401 | `unauthorized` | 返回 JSON；不重定向到页面 |
| 登录凭据错误 | 401 | `invalid_credentials` | 不区分“用户不存在”和“密码错误” |
| 账号未分配业务角色 | 403 | `role_missing` | 本地管理员等非业务账号不能登录业务接口 |
| 对象不存在 / 不在可见范围 / 直接改 ID | 404 | `not_found` | 越权读取不泄露对象是否存在 |
| 可见但角色不允许该动作 | 403 | `forbidden` | 例如业务员尝试批准 |
| CSRF 校验失败 | 403 | `csrf_failed` | 登录与退出同样校验 |

错误体统一为 `{error: {code, message, details}, request_id}`；`request_id` 每次请求生成，供日志与排障对齐。

### 6.2 session 与 CSRF 的调用方式

- 身份用 Django session cookie；写请求必须带 `X-CSRFToken` 头（Django 默认头名）。
- 客户端先执行任意带 session 认证的 GET（如 `GET /api/v1/me`）。即使返回 401，响应也会种下 `csrftoken` cookie；随后把 cookie 值放入 `X-CSRFToken` 即可登录。未登录 GET 不创建业务对象，也没有进度副作用。
- 带 session 的写请求，其 CSRF 校验由公共认证器 `apps.accounts.auth.session_auth` 统一完成：新增写端点只要声明 `auth=session_auth`，就不要在视图里重复调用 `check_csrf`。认证器先判身份再判令牌——匿名写请求是 401，已登录缺令牌才是 403 `csrf_failed`。
- 登录成功会轮换 session，同时轮换 CSRF 令牌（Django `rotate_token`）。客户端登录后必须重新读取 `csrftoken` cookie，再发退出或其它写请求，否则会得到 `csrf_failed`；这是实测踩到过的坑，前端 `web/api.js` 必须按此实现。
- 退出只是结束会话，不删除业务数据。
- 浏览器同源页面由前端 `web/api.js` 统一处理上述 cookie/头；不要在前端硬编码令牌。

### 6.3 角色动作矩阵（服务端强制）

| 动作（服务层常量） | 供应商 | 业务员 | 专家 | 前置条件 |
|---|---|---|---|---|
| `read` | ✓ 本人任务 | ✓ 被授权任务 | ✓ 被授权任务 | 可见性由任务归属决定 |
| `version.create` | ✓ 本人任务 | ✗ | ✗ | 只能在原任务下追加版本（R07） |
| `confirmation.write` | ✗ | ✓ 被授权任务 | ✗ | 不覆盖供应商原值与 AI 建议 |
| `submission.create` | ✗ | ✓ 被授权任务 | ✗ | 整批提交，快照不可变 |
| `decision.resolve` | ✗ | ✗ | ✓ 被授权任务 | 业务员尝试批准返回 403 |

补充约定：

- 可见范围：供应商=`Task.supplier` 本人；业务员/专家=`TaskAssignment` 中角色与账号角色一致的授权行；无授权即 404。首期不按“角色是业务员”放开全部任务。
- 文件、附图、商品、执行、提交、决定统一归一到所属任务做同一套校验；新增业务对象必须在 `permissions._TASK_PATH` 登记归属路径。
- 站内消息按 `recipient` 过滤，他人消息与不存在的消息同样 404。
- `allowed_actions` 只帮助页面展示；服务端每次重新校验，不信任前端传入。
- 权限拒绝在服务层抛 `AuthenticationRequired` / `Http404` / `PermissionDenied`，由 API 层统一转成上表 JSON；业务端点不自行拼错误体。

### 6.4 幂等与并发（P02 起实现，P01 已备基础）

- 写动作的 `Idempotency-Key` 语义（D3 第 1 节）由 P02 实现；数据库侧已用唯一约束兜底：`Submission(task, version, revision)`、`Confirmation(item, revision)`、`FileVersion(task, number)` 等。
- 人工修改携带 `expected_revision`，与 `Item.revision`/`Task.revision` 冲突时返回 409；409 的具体实现和错误码由 P02 发布，P01 只固定字段与语义。

| `contracts/fixtures/DEMO-SET.json` | fixture 模式的完整数据集，由 `make contracts` 从演示数据导出 |

演示壳路由不参与 API 契约、不写数据库、不校验业务权限；`/demo/` 仅供本地开发与演示，正式部署不挂载。

### 8.2 两种模式

- **live**：走 `/api/v1/`，真实会话与对象权限生效；AI 结果仍是 mock，页面必须显示 MOCK 标识。
- **fixture**：`?mode=fixture` 读 `DEMO-SET.json`，不发任何 API 请求；页面必须显示“不校验权限、不写库、不能当作接口可用性证明”。

两个 adapter 暴露同样方法（`me`/`login`/`logout`/`listTasks`/`getTask`/`listItems`/`getItem`/`getRun`），业务代码不写 mock 分支。

### 8.3 客户端规则

- 页面启动先 `GET /me` 判定身份；匿名 401 属正常流程，不是错误。
- 登录成功会轮换 CSRF（第 6.2 节），`api.js` 必须在 `login()` 之后重读 `csrftoken`，不能复用登录前的值。
- 任务/版本/商品/执行各自持有请求令牌；切换版本或商品后，晚到的旧响应必须丢弃（`state.js::isCurrent` + `version_id` 双重校验，对应 FIX-09），不得填入当前卡片。
- 错误按 401/403/404/409/501 分类显示；`allowed_actions` 只用于展示按钮，演示壳点击写动作统一提示 501，不伪造成功。
- 空值与未执行分开呈现：阶段值 `value=null` 且带 `source_id` 显示“未给出建议”，无 `source_id` 显示“—”。

### 8.4 数据来源与限制

- `DEMO-SET.json` 由真实 ORM 序列化，`tasks`/`items`/`cards`/`runs` 与 live 端点逐字段同构；`tests/p02/test_web_shell.py` 用 live 响应做等值断言，schema 漂移会立刻失败。
- 演示账号密码 `customs-demo-only` 由 `make seed-demo` 建立，仅本地使用；fixture 模式的身份是占位符，不是账号。
- 演示壳不实现上传、确认、提交、退回、决定、导出等写流程；这些仍按第 2 节由 P06/P09/P10/P20 交付。

## 10. P06 真实上传、版本与认领（2026-11-17）

本节覆盖前文仍把 P06 写成 501 的历史描述。保留契约 v1.1.0，新增 schema 位于
`contracts/schemas/imports/`，由 `apps/reviews/import_schemas.py` 和 `make contracts` 发布。
HTTP 上传为真实 ORM/受控文件；引擎仍是 `result_mode=mock`、`executor_mode=inline`。

| 方法与路径 | 输入/权限 | 输出 |
|---|---|---|
| `POST /tasks` | 供应商，multipart `file`，必填 `Idempotency-Key` | `ImportOut`，新任务/V1/解析状态/唯一预审引用 |
| `POST /tasks/{task_id}/versions` | 本人供应商任务，multipart `file, expected_current_version_id, confirm_duplicate=false`，幂等键 | `ImportOut`，新增版本，全表重新处理 |
| `GET /tasks/claimable` | 活跃业务员，`limit/cursor`，共用可插拔范围策略 | `ClaimablePage`，只有 `task_id, created_at, assignment_status` |
| `POST /tasks/{task_id}/claim` | 业务员且可认领，幂等键；空 body | `ClaimOut`，认领人和时间；同事务授予 TaskAssignment |
| `GET /versions/{version_id}/import` | 版本对象 `read` 权限 | `ImportDetail`，状态、错误、P04 完整定位报告 |
| `GET /files/{file_id}` | 版本或图片所属任务 `read` 权限 | 原件或图片字节，private/no-store；file_id 只接受版本/图片 UUID |

`file.import`、`task.claim`、`task.claim.list` 是上传/候选池动作。认领候选权限不能替代对象 `read` 权限。
`task.claim` 在新建授权前校验候选范围；已有本人 TaskAssignment 时允许幂等重放。默认本试用空间内所有
活跃业务员可见最新版本已成功解析且尚未授权业务员的任务；未来通过 `CUSTOMS_CLAIM_SCOPE_POLICY` 收窄。
供应商和专家调用认领池为 403，未登录为 401；未认领业务员读取商品、原件、图片、结果仍为 404。

请求幂等键长度 1–128。`file.import` 指纹包含目标任务、文件 sha256、净化后文件名、预期版本和重复文件确认意图。
同 key 同内容复用持久凭据；失败后同 key 可继续未完成处理；成功后同 key 只读重放，不再预审。
同 key 不同内容返回 `idempotency_conflict`。不同 key 的主动上传是新意图；同任务命中相同 sha256 时
先返回 `duplicate_file`，确认请求使用新的 key 和 `confirm_duplicate=true`。不同首次上传请求创建独立任务。

结构阻断清单：

| 类别 | 具体规则/代码 |
|---|---|
| 工作簿/页签/表头 | P04 `OoxmlError/SemanticLayoutError`：损坏包、缺工作簿、缺/歧义页签、缺表头、缺必需语义列、重复必需语义列 |

| 商品识别 | 空申报集合、商品品名为空；可定位且超出既有来源/品名/成员字段长度限制 |
| 归属歧义 | 多条申报行争抢同一装箱成员，`ambiguous_member_ownership`；不任选、不静默少落成员 |

不额外阻断原 HS、申报要素、退税率空白；这些原文由后续业务核查。P04 无匹配 `missing_packing_member`

## 11. P13 后台执行与重试（2026-11-17）

本节覆盖此前把 prechecks/retries 写成 501、上传只支持 inline 的历史描述。发布契约 **1.2.0**，保留现有 RunStatus；使用 rq 时要求 PostgreSQL，模型仍为 mock。未实现的其余端点继续明确返回 501。

| 方法与路径 | 输入/权限 | 输出 |
|---|---|---|
| `POST /versions/{version_id}/prechecks` | 当前可编辑版本；业务员 confirm 权限；body `revision`；必填幂等键 | RunCreated，创建新一轮，旧轮保留 |
| `POST /runs/{run_id}/retries` | 当前已结束执行中的失败 `item_ids`；预审 confirm、专家核查 decide 权限；必填幂等键 | RunCreated，带 parent_run_id；只重新调用选中失败行，其他行带来源沿用 |
| `GET /runs/{run_id}` | 对象 read 权限，仅查询 | RunDetail，逐行实际状态、attempt_history、origin_run_id、retry_allowed/retry_item_ids |

两项 POST 同用现有 session/CSRF/权限与错误信封。队列未启用返回 409 `queue_required`，旧版本/修订冲突返回 409，非法失败行选择返回 422。幂等身份绑定目标版本/执行和请求内容；同 key 重放不创建新轮。

TaskDetail 增加 `precheck_allowed`；前端按服务端能力显示操作。RunItemEntry 的 attempts 允许 0：排队未调用或本轮沿用行不冒充一次新调用。部分技术失败与业务无法确认分别展示，run succeeded 不等于整表审批通过。

rq 上传返回 `parse_status=staged, executor_mode=rq`，后台导入成功后自动预审；页面轮询导入与执行。上传请求仍同步做结构预校验。提交成功同事务登记专家核查，默认专家授权沿用原规则。Redis 故障不把已提交请求改成失败，扫描器负责补投和租约恢复。

`/uploads/` 接入逐行进度、失败行重试和重新预审，仍为开发验收页；`/demo/` 演示壳不因此变为可审批页面。运行、恢复及实际验收边界见 [P13 交接](交接/P13.md)。

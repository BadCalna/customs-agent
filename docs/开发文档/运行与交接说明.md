## 1. 开发环境

从仓库根目录运行以下命令。本机验证环境为 macOS、uv 0.11.18、Python 3.14.4、Django 5.2.19 和 Django Ninja 1.8.0。需要 make 和 uv，首次安装依赖时需要可访问包源或已有缓存。uv 依据 `.python-version` 选择 3.14，并按 `uv.lock` 安装到 `.venv-customs/`。PyCharm 可选择 `.venv-customs/bin/python` 作为解释器。

```sh
make setup
make migrate
make seed-demo        # 建立三角色开发账号与演示任务（幂等）
make check
make test TASK=P00
make test TASK=P01
make test TASK=P02
make dev
```

服务默认位于 `http://127.0.0.1:8000`。打开 `/api/health`、`/api/docs`、`/api/v1/docs`、`/admin/` 或 `/demo/`（P02 组件演示壳），用 Ctrl+C 停止服务。端口占用时可运行 `make dev BIND=127.0.0.1:8001`。也可以直接运行 `make demo-components`：它一次完成契约演示数据、DEMO-SET 导出并启动服务，然后打开 `http://127.0.0.1:8000/demo/`。需要进入管理后台时，先运行 `.venv-customs/bin/python manage.py createsuperuser` 交互创建自己的本地管理员。

PyCharm 可从运行配置下拉框选择 `customs-agent Django`，共享配置位于 [.run/customs-agent-django.run.xml](../../.run/customs-agent-django.run.xml)。配置类型为 Python，解释器选 `.venv-customs/bin/python`，脚本选项目根目录的 `manage.py`，参数填 `runserver 127.0.0.1:8000`，工作目录选项目根目录。首次运行前执行上面的 setup 和 migrate。若解释器列表尚未登记该环境，通过“添加本地解释器”选择现有的 `.venv-customs/bin/python`。

P01 引入自定义账号模型 `accounts.User`（`AUTH_USER_MODEL`）。P00 时期创建的本地 SQLite 库不能直接复用，需删除 `.local/db.sqlite3` 后重新 `make migrate`；该库只有工程自验数据，删除前确认其中没有要保留的演示内容。全新工作区按上面顺序执行即可。

各 Agent 独立数据库和文件目录；只共享代码、迁移、合成/脱敏样例。真实模板、供应商资料、数据库、密钥和日志不提交 Git。系统启动不得在未确认位置自动覆盖已有数据库或原文件。

| 配置语义（变量名由 P00 固定） | 本地默认 | 何时必须配置 |
|---|---|---|
| 数据库后端及连接信息 | 本地 SQLite 文件（`CUSTOMS_SQLITE_PATH`）；`CUSTOMS_DB_BACKEND=postgres` 时读 `CUSTOMS_PG_*`，缺变量启动即失败 | P12 已支持；试用/生产切 PostgreSQL |
| 页面数据模式 | live；组件演示可单独选 fixture | P02 组件演示入口 |
| 引擎模式 | mock，页面有明确标识 | P16/P18 真实 AI 接入 |
| 执行器模式 | inline，只跑短时 mock | P13 rq 模式需要 Redis/worker |
| 原文件、图片、导出根目录 | `.local/files`（`CUSTOMS_FILE_ROOT`，相对路径按仓库根解析）；按 `tasks/<task>/versions/<version>/{original,images,exports}` 分目录，Git 忽略 | P05 已提供受控存储；P06 接上传与解析流程，P20 接导出业务 |
| 模型与查询源 | 空；P14/P17 查询源未配置时明确返回 `source_unconfigured` | 真实模式/P14～P18 接入时；见 2.5、2.6 |
| 钉钉 DWS 连接/接收人映射 | mock 通道 | P19 测试环境；真实发送按授权范围 |

P05 受控存储配置（2026-11-16 落地）：

- `CUSTOMS_FILE_ROOT`：存储根，默认 `BASE_DIR/.local/files`；可用环境变量覆盖，相对路径按仓库根解析。
- `CUSTOMS_FILE_MAX_BYTES`：单次保存原件/导出副本上限，默认 104857600（100 MB）。
- `CUSTOMS_IMAGE_MAX_BYTES`：单张附图上限，默认 20971520（20 MB）。
- `CUSTOMS_FILE_READ_MAX_BYTES`：受控读取单文件上限，默认 209715200（200 MB）。
- 三个上限必须是正整数（字节数）；环境变量解析失败时启动直接报 `ImproperlyConfigured`，不静默回退。
  暂存与发布必须使用同一上限；服务层 `stage_version_original` / `publish_staged_version_original`
  都读取 `CUSTOMS_FILE_MAX_BYTES`，不要在发布阶段另传更小值。
- 原件路径 `tasks/<task>/versions/<version>/original/<sha256>.<ext>`，图片 `.../images/`，
  导出副本 `.../exports/<kind>/<sha256>.<ext>`；按内容寻址、只增不覆盖，不提供业务删除入口。
- 备份范围必须同时包含数据库与 `CUSTOMS_FILE_ROOT`；恢复后按 `storage_path` 重新核对 sha256。
- P06 推荐顺序：先 `files.stage_version_original` 落暂存，数据库事务提交后
  `files.publish_staged_version_original` 原子发布并写 `storage_path`；事务回滚则 `storage.discard_staged`，
  避免孤件与半个任务。同一 token 的发布由 `incoming/<token>.lock` 串行化并原子绑定目标版本：
  同目标并发/重复发布返回同一正式路径，跨目标并发只有一方成功且失败方不产生正式文件。

## 2.5 查询来源接入（P14）

P14 的 HS 税则与申报要素适配器不联网、不建表，只读取本地 JSON。**没有默认样本**：未配置时查询返回 `query_status=source_unconfigured`、`evidence_status=query_failed`，不会启动失败，也不会拿合成数据冒充真实来源。

| 环境变量 | 指向 | 对应文件 |
|---|---|---|
| `CUSTOMS_TARIFF_PATH` | 税则数据 JSON | `adapters/sources/hs_lookup.py` |
| `CUSTOMS_DECLARATION_ELEMENTS_PATH` | 申报要素清单 JSON | `adapters/sources/declaration_elements.py` |

文件格式以 `tests/p14/fixtures/*.json` 为可运行样例（**合成数据，不能作为申报依据**）：

- 税则：`schema_version=p14.tariff.1`、`dataset`、`versions[]`、`codes[]`；
- 要素：`schema_version=p14.elements.1`、`dataset`、`versions[]`、`schemas[]`；
- 两个文件的 `versions` 用 `version/effective_from/effective_to` 声明有效期；同一日期只能落在一个版本，否则查询按“版本不唯一”保持待核；
- 税则 `codes[]` 每条记录还要按来源填写自身的 `effective_from`/`effective_to`（来源没有就给空，不推断）。查询会用**业务申报日期**核对记录有效期；日期早于生效或晚于失效，或没有申报日期时，一律不标 `declaration_ready`。只填版本、不填业务日期，不能得到“可申报”结论；
- 每条编码/清单必须有 `source.document` 与 `source.locator`，否则导入自检直接拒绝；没有真实 URL 就留空，不编造。

### 导入与复核步骤

1. 从官方渠道或 Jay 授权的导出取得当期税则/《规范申报目录》，保留公告号、版本、取得日期；
2. 按上述结构转换成 JSON，逐条填 `source.document`/`locator`/`retrieved_at`；
3. 自检（不连库、不联网）：

   ```sh
   .venv-customs/bin/python - <<'PY'
   from adapters.sources.hs_lookup import JsonTariffStore
   from adapters.sources.declaration_elements import JsonElementStore
   import os
   print(JsonTariffStore(os.environ["CUSTOMS_TARIFF_PATH"]).load())
   print(JsonElementStore(os.environ["CUSTOMS_DECLARATION_ELEMENTS_PATH"]).load())
   PY
   ```

4. 关务人员复核后，把 `dataset.review_status` 改为 `reviewed`，填 `reviewed_by`、`reviewed_at`；**导入人不能自己冒充复核人**；
5. 设置两个环境变量并重启服务；未复核或第三方数据仍可查，但 `authoritative=false`，不得产出“充足/可申报”的结论；
6. 复跑 `make test TASK=P14`，再用真实编码做一次查询，核对证据定位、版本日期与编码状态。

### 常见状态与处理

| 现象 | 含义 | 处理 |
|---|---|---|
| `source_unconfigured` | 环境变量未设 | 按上表配置；不要临时指向测试夹具 |
| `source_unreadable` | 文件不存在/JSON 损坏/字段不合契约 | 按报错的文件名与行号修数据；修不好就保持失败，不要回退到合成样本 |
| `version_unverified` | 缺申报日期/税则版本，或日期不在已收录窗口 | 让业务员补业务日期或确认版本；系统不填拟申报日期 |
| `HS_RECORD_NOT_EFFECTIVE` | 编码记录生效/失效日期与申报日期冲突 | 换用该日期有效的编码，或转专家核对；不能看 `active` 就直接申报 |
| `HS_EFFECTIVE_DATE_UNKNOWN` | 只有版本、没有业务申报日期 | 补业务日期；系统不拿当天代替 |
| `HS_RECORD_EFFECTIVE_UNVERIFIED` | 编码记录只给了一端有效期 | 回来源补全生效/失效日期；不能按未核实区间申报 |
| `not_found`（版本已核） | 本版本未收录该编码/清单 | 记来源覆盖缺口，不宣称编码无效或无需申报要素 |
| `sufficiency=unverified` | 来源/版本/解析/条件待确认 | 转专家或人工核对；**不得生成供应商补料单** |
| `sufficiency=insufficient` | 权威已复核版本下确有必填缺失/非法 | 才可导出 `supplement_items` 向供应商补料 |

年度换版：新增一个 `version` 窗口，旧版本保留以便回查；不要覆盖旧文件，也不要把新旧版本的要素清单混在同一 `version` 下。真实数据、复核人、公告号属于内部资料，不提交 Git。

## 2.6 退税与监管来源接入（P17）

P17 的出口退税率与监管条件适配器同样**不联网、不建表**，只读本地 JSON；**没有默认样本**，
未配置时返回 `query_status=source_unconfigured`、`evidence_status=query_failed`，结论保持
`unknown`，不会启动失败，也不会拿合成数据冒充真实政策依据。退税与海关税则**分库管理**：
退税率来自税务/财政体系，不能与 `CUSTOMS_TARIFF_PATH` 混用一个文件。

| 环境变量 | 指向 | 对应文件 |
|---|---|---|
| `CUSTOMS_TAX_RATE_PATH` | 出口退税率/退税政策 JSON | `adapters/sources/tax_lookup.py` |
| `CUSTOMS_REGULATORY_PATH` | 监管条件/检验检疫要求 JSON | `adapters/sources/regulatory_lookup.py` |

文件格式以 `tests/p17/fixtures/*.json` 为可运行样例（**合成数据，不能作为申报依据**）：

- 退税率：`schema_version=p17.taxrate.1`、`dataset`、`versions[]`、`rates[]`；
- 监管条件：`schema_version=p17.regulatory.1`、`dataset`、`versions[]`、`records[]`；
- 两个文件都用 `versions` 的 `version/effective_from/effective_to` 声明有效期；同一日期只能落在
  一个版本，否则按“版本不唯一”保持待核；
- 每条记录必须有 `source.document` 与 `source.locator`，否则导入自检直接拒绝；没有真实 URL 就留空。

退税率记录的三个必填口径（导入期强制，写错直接报错而不是猜）：

1. `rate_kind` 与 `rate_percent` 必须一致：`export_rebate` 给正数、`zero_rate` 必须是 0、
   `exempt/not_refundable/not_applicable/unknown` 必须为空（**不得补 0**）；
2. `rate_raw` 保留来源原文（如 `"13%"`、`"0"`、`"不予退税"`），否则无法回查；
3. `conditions` 的三种写法含义不同：**不写该字段**＝来源未声明（待核）；**写 `[]`**＝来源明确
   无条件限制；**写非空数组**＝有条件但未机读化（转专家）。条件要么同时给 `document` 与 `locator`，
   要么都不给（只给一半会被拒绝）。

监管记录的两个必填口径：

1. `direction` 必须是 `import`/`export`/`both`；**`both` 不能带具体措施**——来源表里 A 类进口、
   B 类出口请拆成两条方向明确的记录；
2. `measures`：不写该字段＝来源未声明（待核）；写 `[]`＝来源明确声明无监管要求；非空数组＝有要求。
   措施 `name`/`agency` 只填来源原文；来源只给代码就留空，运行时会报 `REG_MEASURE_NAME_UNKNOWN`
   并转专家，**不要自己补含义**。两用物项线索放 `dual_use`，不需要填判定结论。

### 导入与复核步骤

1. 从电子税务局/离线申报工具、单一窗口或 Jay 授权的导出取得当期退税率文库与监管条件表，
   保留公告号、文库版本、取得日期；
2. 按上述结构转成 JSON，逐条填 `source.document`/`locator`/`retrieved_at`；
3. 自检（不连库、不联网）：

   ```sh
   .venv-customs/bin/python - <<'PY'
   import os
   from adapters.sources.tax_lookup import JsonTaxRateStore
   from adapters.sources.regulatory_lookup import JsonRegulatoryStore
   print(JsonTaxRateStore(os.environ["CUSTOMS_TAX_RATE_PATH"]).load())
   print(JsonRegulatoryStore(os.environ["CUSTOMS_REGULATORY_PATH"]).load())
   PY
   ```

4. 关务人员复核后把 `dataset.review_status` 改为 `reviewed`，填 `reviewed_by`、`reviewed_at`
   （导入人不能自己冒充复核人）；`source_type` 用 `official_tax`/`official_finance`/
   `official_regulatory`/`official_dual_use`，第三方只能声明 `unverified_third_party`；
5. 设置两个环境变量并重启服务；未复核或第三方数据仍可查，但 `authoritative=false`、
   `usable_as_basis=false`，不能产出“退税率已适用”或“无监管”的结论；
6. 复跑 `make test TASK=P17`，再用真实编码做一次查询，核对证据定位、版本日期、方向与措施名称。

### 常见状态与处理

| 现象 | 含义 | 处理 |
|---|---|---|
| `source_unconfigured` | 环境变量未设 | 按上表配置；不要临时指向测试夹具 |
| `source_unreadable` | 文件不存在/JSON 损坏/字段不合契约 | 按报错的文件名与行号修数据；修不好就保持失败，不要回退到合成样本 |
| `applicability=unknown`（退税） | 缺申报日期/来源未声明条件/来源未声明处理方式/来源非权威/8 位子目 | 补业务日期；向关务专家确认条件与政策状态；不要读成 0% 或“不予退税” |
| `TAX_RATE_NOT_FOUND` | 该期文库未收录该税号 | 记来源覆盖缺口，补文库或转专家；**不能按 0% 处理** |
| `TAX_CONDITION_NOT_DECLARED` | 来源没写适用条件 | 回来源补条件说明；不要推定“无条件适用” |
| `TAX_RATE_CONFLICT` | 原表退税率与文库不一致 | 转专家按政策原文判定，不由适配器裁定 |
| `REG_DIRECTION_UNKNOWN` | 没给进出口方向 | 由业务员/上传数据补方向；系统不默认方向 |
| `REG_MEASURES_NOT_DECLARED` | 来源没写监管要求字段 | 回来源补该字段；**不等于无监管** |
| `REG_MEASURE_NAME_UNKNOWN` | 只有代码没有名称/机关 | 补官方代码表；不要靠模型或记忆补 |
| `REG_MEASURE_CATEGORY_UNKNOWN` | 措施没说类别（证件/检验检疫/两用物项） | 回来源补类别；类别不明时监管结论不算核清 |
| `REG_MEASURE_DUAL_USE_UNVERIFIED` | 两用物项写在“监管措施”里（`category=dual_use`） | 与 `dual_use[]` 同等对待：转专家判定，不能当已核清 |
| `REG_SUBHEADING_ONLY` / `TAX_SUBHEADING_ONLY` | 只有 8 位税目/子目 | 补 10 位申报编码；8 位一律不可作依据（“来源声明无监管/退税率一致”也不例外） |
| `TAX_RATE_NOT_COMPARED`（`rate_comparison=not_compared`） | 原值与来源不可数值比对（原值空白、来源是“不予退税/免税”等） | 转专家核对政策原文；`expert_review_required` 为 true 时不能自动通过 |
| `REG_DUAL_USE_UNVERIFIED` | 命中两用物项清单线索 | 转专家按技术参数、最终用途与用户判定；不改名规避 |
| `outcome=declared_none` 但 `usable_as_basis=false` | 来源这么说，但来源非权威/不可定位 | 补齐复核与定位后才可读作“无监管” |

年度换版：新增一个 `version` 窗口，旧版本保留以便回查；不要覆盖旧文件，也不要把新旧文库混在
同一 `version` 下；政策调整只靠 `rate_state=abolished/superseded` 就地标注，不要删行。
真实数据、复核人、公告号属于内部资料，不提交 Git。

### 5.3 备份与恢复

脚本在 `scripts/operations/`（说明见同目录 README）：

- **备份**：停止当前运行的 app/web/worker 等写入服务（结束后只恢复原运行服务），使用一次性容器读取实际 `CUSTOMS_FILE_ROOT`；数据库 dump + 文件包 + 行数/稳定内容指纹/文件哈希清单；状态和日志在备份外留档。
- **恢复**：只恢复进**隔离目标**（新库 + 新目录），拒绝已有对象和生产/原件祖先后代目录；清理须验证本次创建对象的身份，不覆盖旧对象。
- **演练**：`drill.sh` 内部调用备份/恢复/验证，不再解析日志尾行；stdout 为 JSON、诊断在 stderr。失败保留隔离证据；通过后可清理本次创建目标。
- **一致性边界**：Compose 默认停写仅覆盖该部署服务，外部写入者仍须协调；native 模式无法自动停写。`--no-quiesce` 的 dump、文件包与清单为三个相邻时点，不得当作一致备份；`incoming/` 半成品不进备份。
- **回退**：不做降级迁移。恢复出旧库/旧目录后改 `CUSTOMS_PG_NAME`/`CUSTOMS_FILE_ROOT`，只重启 `app`/`web`，原库与原文件保留待排查。

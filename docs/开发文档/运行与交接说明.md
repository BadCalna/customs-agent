## 1. 开发环境

从仓库根目录运行以下命令。本机验证环境为 macOS、uv 0.11.18、Python 3.14.4、Django 5.2.19 和 Django Ninja 1.8.0。需要 make 和 uv，首次安装依赖时需要可访问包源或已有缓存。uv 依据 `.python-version` 选择 3.14，并按 `uv.lock` 安装到 `.venv-customs/`。PyCharm 可选择 `.venv-customs/bin/python` 作为解释器。

```sh
make setup
make migrate
make check
make test TASK=P00
make dev
```

服务默认位于 `http://127.0.0.1:8000`。打开 `/api/health`、`/api/docs` 或 `/admin/`，用 Ctrl+C 停止服务。端口占用时可运行 `make dev BIND=127.0.0.1:8001`。需要进入管理后台时，先运行 `.venv-customs/bin/python manage.py createsuperuser` 交互创建自己的本地管理员。

PyCharm 可从运行配置下拉框选择 `customs-agent Django`，共享配置位于 [.run/customs-agent-django.run.xml](../../.run/customs-agent-django.run.xml)。配置类型为 Python，解释器选 `.venv-customs/bin/python`，脚本选项目根目录的 `manage.py`，参数填 `runserver 127.0.0.1:8000`，工作目录选项目根目录。首次运行前执行上面的 setup 和 migrate。若解释器列表尚未登记该环境，通过“添加本地解释器”选择现有的 `.venv-customs/bin/python`。

本地设置可直接用默认值，也可复制 `.env.example` 到 `.env` 调整，进程环境变量优先。`make setup` 首次创建 `.local/dev-secret`，重复运行会沿用该密钥。SQLite 默认使用 `.local/db.sqlite3`。P00 使用 `CUSTOMS_PAGE_MODE=live`、`CUSTOMS_ENGINE_MODE=mock` 和 `CUSTOMS_EXECUTOR_MODE=inline`。保留页面 fixture 配置供 P02 使用，real 引擎或 rq 执行器会在启动时报错。主控维护 config、Makefile、依赖和公共路由；模块测试各放在对应的 `tests/pxx/`。

各 Agent 独立数据库和文件目录；只共享代码、迁移、合成/脱敏样例。真实模板、供应商资料、数据库、密钥和日志不提交 Git。系统启动不得在未确认位置自动覆盖已有数据库或原文件。

| 配置语义（变量名由 P00 固定） | 本地默认 | 何时必须配置 |
|---|---|---|
| 数据库后端及连接信息 | 本地 SQLite 文件 | P12 PostgreSQL 联调及试用 |

## 2. 统一命令交付

当前可运行 setup、migrate、dev、check 和 test TASK=P00。下表同时列出后续任务将提供的命令。

| 命令约定 | 应完成的动作 | 提供者 |
|---|---|---|
| `make setup` | 安装锁定依赖、检查解释器、提示本地配置 | P00 |
| `make migrate` | 当前配置数据库执行已提交 Django 迁移 | P00/P01 |
| `make dev` | 启动本地服务，打印地址；可访问 `/admin/` 与 `/api/docs` | P00 |
| `make check` | Django system check、代码基本检查及迁移漂移检查 | P00/P01 |
| `make seed-demo` | 幂等建立三角色测试账号与显式归属的模拟任务；不重置已有业务资料 | P01/P02 |
| `make test TASK=P07` | 运行该任务约定的必要测试；未知任务/没有验证入口不能假通过 | P00 提供入口，各包补实际检查 |
| `make test-contracts` | schema、固定 JSON、端点和 OpenAPI 一致性检查 | P02 |
| `make demo-components` | 启动可打开的 fixture 组件演示入口 | P02，P07/P08/P11 扩展 |
| `make check-postgres` | 确认当前为 PostgreSQL，执行数据库兼容和并发相关检查 | P12/P13 |
| `make worker` | 启动指定队列的 worker，配置缺失明确失败 | P13 |
| `make test-integration` | 执行选定数据库/引擎模式下的真实业务链路 | P21 |

每个任务包必须补实际运行命令、退出码、结果和模式。测试通过只针对其实际环境，不能把未启动的浏览器或未配置的数据库写成已验证。

## 3. SQLite 切换 PostgreSQL 的门槛

P12 在真实 Web + worker 并行写入前执行，且进入多人试用前必须通过。Agent 负责本地/容器安装方案、数据库初始化、连接配置和验证，Jay 无需为了写骨架先购买云数据库。

交接记录必须包含：

- 空 PostgreSQL 从同一套 Django migrations 初始化的证据；必要约束、外键、索引和唯一性检查。
- SQLite 演示数据是否保留的明确决定。默认只重建可重复演示数据；有需保留的数据时先备份、导入、比对数量/关联和附件引用，不直接删除旧库。
- 同一组正常、权限、提交和版本测试的数据库结果差异；真正的并发验证要用多连接/进程，不能只串行发两次请求。
- 回退所需的数据库与文件备份、旧配置和操作顺序；生产环境不允许通过随意降级迁移丢数据。

# AI 智能关务：开发任务与阶段交付计划

版本：1.0，2026-11-13。2026-11-14 实施进度：P00 技术自验通过，Jay 手工测试待进行，实际可用命令见 [D6](运行与交接说明.md)。

本轮按 Jay 最新决定重新组织：Django 为主框架，SQLite 起步，全量使用 Agent 开发；每个可拆分任务都必须约定前置条件、衔接文档、交付物和验收。Django Ninja 作为本轮默认 API 方案，与 Django 共用账号、ORM 和迁移，不额外引入 FastAPI 服务。

## 1. 本期目标与不变规则

完成“供应商上传文件 → 自动预审 → 业务员确认 HS 并提交 → 自动专家 AI 核查 → 专家人工通过或退回 → 保留版本与导出”的多人系统。系统内 AI 提供可替换的建议能力；权限、任务状态、提交和审批由业务服务控制。

依据：[D1 业务与流程约定](阶段0/业务与流程约定.md) v0.4、[D2 数据与版本约定](阶段0/数据与版本约定.md) v0.2、[D5 验收用例与记录](阶段0/验收用例与记录.md) v0.2，以及本轮技术栈与全量 Agent 开发决定。

- 首次上传一个 Excel 建一个审核任务；补料在原任务下新增版本。
- 商品按申报要素页签的申报记录建立；装箱明细为关联成员；保存各版本页签、行、单元格和附图映射。
- 解析、关联和版本留存完成后自动预审；保留重新预审和单行失败重试入口。
- 补料不带系统商品 ID；新版所有商品重新预审，不继承旧行身份、建议或审批。跨版本对照只是候选展示。
- 业务员确认并提交的 HS 进入不可变提交快照，随后自动启动专家 AI 核查。后续编辑不得改变已提交输入。
- 专家可改码后通过，必须记录前后值和原因；首期整任务通过，不能部分商品先通过；AI 不自动审批。
- 三角色登录和服务端权限在首版范围内；首期一名专家，无分派。站内消息及业务员、专家节点的钉钉 DWS 通知保留。
- 原文件、原值、历次 AI 输出、人工值及修改记录分别保存。拟申报日期不由系统填写。导出不改变退回、发送或审批状态。
- 支持现有多页签模板，重点验证 WPS DISPIMG；原有其他页签和意见保留。不扩展上游材料溯源、ERP 接口、物流审批或自动报关。

## 2. 技术栈与运行模式

| 部分 | 本轮方案 | 落地边界 |
|---|---|---|
| 后端 | Django + Django Ninja，模块化单体 | 一个工程、一套认证/模型/迁移；API 只做校验和调用，业务服务负责状态与持久化 |
| 数据库起步 | SQLite，每个 Agent 工作区独立数据库 | 用于本地骨架、单进程模拟闭环、组件开发；不共享运行中的 `.sqlite3` 文件 |
| 联调数据库 | PostgreSQL，P12 专项切换 | 真正 Web + worker 并行写入和多人试用前启用；在 PostgreSQL 上验证事务、重复提交和过期回写 |
| 后台执行 | 先短时同步模拟执行器；后接 Redis + django-rq | 早期模拟不调用外部模型；真实耗时调用放入 worker；页面和引擎契约保持一致 |
| 前端 | HTML/CSS/JavaScript，复用现有原型的布局与样式 | 抽出 API 访问、局部 UI 状态和组件；后端拥有业务状态；本期不并行迁移 Vue |
| 文件 | 本地受控文件存储 + 可替换解析/导出适配器 | 原件不可变，文件下载同样校验权限；Excel 库由 P03 的保真试验决定 |
| 检查 | Django 测试 + 契约样例校验 + 关键浏览器流程 | 按任务风险验证；不以覆盖率数字或只有正常路径作为通过依据 |
| 部署 | 本地开发；试用时单机服务或 Docker Compose | P22 给出一套可执行方案，不引入微服务和 Kubernetes |

Python 与依赖版本由 P00 核对兼容性后锁定并写入 D6。可以从 Python 3.12、Django 5.2 系列作为候选开始；实际可复现的锁文件为准，不依赖电脑自带 Python 或要求 Jay 手工拼装环境。

SQLite 与 PostgreSQL 切换需要运行同一套迁移、处理需保留的数据，并复验约束与事务。SQLite 上的 `select_for_update()` 不提供对应行锁保证，不能用 SQLite 测试结果证明并发正确。开发阶段优先可迁移的 ORM 字段；关键关系和状态用显式字段，JSON 用于扩展事实与证据。金额、税率等明确精度和空值语义，不借数据库自动推断。

模拟有三个独立开关，在开发配置中集中管理：页面 `fixture/live`、引擎 `mock/real`、执行器 `inline/rq`。页面 fixture 只验证组件；`live + mock + inline + SQLite` 验证真实保存和流程；`live + mock + rq + PostgreSQL` 验证后台任务；最后替换为真实引擎。所有 mock 结果显式标注，不能因界面完整就认定 AI 已接通。

## 3. 全量 Agent 的职责分工

| 角色 | 负责什么 | 交接责任 |
|---|---|---|
| Jay | 业务范围、未决业务规则、优先级与可用性验收 | 提供真实模板、账号/查询源的组织条件；对业务取舍作决定 |
| 主控 Agent | 任务派发、骨架、公共接口、数据模型、迁移、权限和集成 | 发布基线版本；审核执行 Agent 的差异；完成集成验证后更新任务状态 |
| 执行 Agent | 在指定文件范围内实现任务包 | 交代码、必要测试、真实运行记录、接口变更请求及交接说明 |
| 验收 Agent | 根据规则和用例检查关键结果 | 独立读取实现与测试证据，重点复核权限、版本、快照、并发、Excel 保真 |
| 关务专家 | 标注业务样本、裁决专业分歧、确认适用范围 | 专业答案和试用结论；Agent 自己生成的“金标准”不能代替专家答案 |

这里的角色是职责，可以分时由不同会话承担，不要求常驻多个 Agent。起步建议一个主控、最多两个独立执行任务；完成一次成功交接后再增加并行。各 Agent 使用独立分支/工作目录，只有主控写集成分支；不能同时修改同一组公共文件。

编码、测试编写、文档和部署脚本均由 Agent 完成。全量 Agent 开发不消除真实模板验证、业务决策或专业验收，也不能预设“原人工估时除以某个倍数”。

## 4. 实施顺序和进入下一阶段的标准

下表 M0～M5 替代旧计划的严格串行阶段；D1/D2/D5 中旧阶段编号只是历史交付标记。每个任务包另有“编码前置”和“集成前置”，依赖满足的任务可以提前开始。

| 里程碑 | 主要任务包 | 可以演示什么 | 通过标准与交接 |
|---|---|---|---|
| M0 工程和契约就绪 | P00、P01、P02；并行启动 P03 | 本地启动、登录、真实数据库保存、API 文档、模拟数据页面入口 | 新工作区按 D6 可启动；D3/D4 与 schema/样例一致；三角色越权测试通过；主控发布可领取任务的基线 |
| M1 模拟闭环 + 文件能力 | P04～P11；P03 完成保真试验 | 实际文件入库、模拟预审、业务员提交、模拟专家核查、人工通过/退回、V2 重审 | S01～S03 用 mock 结果跑通并标注；旧版本/快照不被覆盖；真实模板解析与初步导出有证据；导出限制明确 |
| M2 PostgreSQL + 后台任务 | P12、P13 | 上传后快速返回，后台解析/预审进度，提交后自动专家核查，单行失败重试 | PostgreSQL 上重复事件、并发提交、worker 中断恢复、旧版延迟回写均验证；不能用 SQLite 单进程记录代替 |
| M3 两阶段真实 AI | P14～P18 | 可定位证据的预审及专家核查 | 独立推荐后比较原码；未取得/查询失败/业务不确定分开；专家样本评测有真实结果；专业质量门槛在评测前约定 |
| M4 完整交付功能 | P19、P20，页面与引擎集成 | 通知、补料清单、保真导出与完整历史 | DWS 测试通道验证；导出绑定明确版本与结果集；原图/公式/意见保留；导出不隐式退回或发送 |
| M5 试用与交接 | P21、P22 | 三角色真实脱敏案例，部署和备份恢复 | 关键验收无阻断；专家给出适用范围；接手 Agent 按 D6 在新环境恢复并复跑；记录未解决限制 |

技术风险早验证：P03 与 P00 并行，查询来源 P14/P17 在契约发布后尽早试接，DWS 的可用方式在 P19 进入真实投递前确认。这些失败只阻塞相关依赖；页面和模拟闭环可以继续。

## 5. 第一批如何派发

| 批次 | 主控线 | 可独立执行线 | 完成标志 |
|---|---|---|---|
| 现在 | P00：建立最小 Django 工程和检查入口 | P03：只读分析模板，使用副本测试 DISPIMG 和插列 | 工程能启动；文件风险有真实试验结论或明确阻塞 |
| 骨架可用后 | P01：核心模型、身份、对象权限；随后 P02：schema、固定样例和 mock 引擎 | 完善 P03 样本映射与导出试验 | 主控发布契约 v1 和启动说明，公共类型不再由各 Agent 自行定义 |
| 契约发布后 | P09/P10：后端提交、审核和版本状态；P12 可独立准备 PostgreSQL | 优先 P07 商品卡片、P08 任务与进度；P04/P05 文件模块按样例开发 | 一个 Agent 的成果可被另一个 Agent 按交接文档接续 |
| 模块可用后 | P06 整合文件入口，P13 整合真实队列 | P11 操作与历史界面，P14/P15/P17 查询适配器 | 模拟闭环和真实后台链路逐步合并，随后接真实模型 |

P00 不依赖模型密钥、Redis 或 PostgreSQL 安装。Jay 当前优先检查真实模板、业务员任务归属方式以及导出专家结果列布局；它们只阻塞相关任务，不阻塞建骨架。工作区必须是实际准备开发的仓库并有写权限，不能在另一个目录悄悄初始化替代项目。

## 6. 工程目录约定

以下为目标目录，随各任务包逐步建立。单体按业务模块划分；复杂基础设施保持在统一适配层中。

| 路径 | 职责 / 维护者 |
|---|---|
| `config/`、`manage.py`、依赖锁文件、`Makefile` | 启动、配置和统一检查命令；主控维护 |
| `apps/accounts/` | 认证、任务范围授权、角色；主控维护 |
| `apps/reviews/` | 审核任务、文件版本、商品、确认、提交、人工审批、日志；模型和迁移由主控维护 |
| `apps/runs/` | 分析执行、单行尝试、调度与持久化结果；主控维护 |
| `apps/notifications/` | 站内消息、投递记录；新增模型仍由主控集成迁移 |
| `contracts/` | API/引擎 schema、枚举、脱敏 JSON 样例；主控发布版本 |
| `adapters/files/`、`adapters/engines/`、`adapters/sources/` | 文件、模型、查询来源的可替换实现；按任务包分文件所有权 |
| `web/` | 页面、组件、统一 `api.js`、局部 UI 状态；公共入口由主控维护 |
| `tests/` | 按任务包归属的契约、服务、集成和浏览器验证 |
| `docs/开发文档/交接/` | 每个任务包的派发基线和回交记录 |
| `data/private/`、`uploads/`、`exports/` | 本地业务样本和运行产物；不提交版本库，各工作区独立 |

架构不额外创造“批次”业务概念。最低数据对象包括 Task、FileVersion、Item、Image、Run/RunItem、Confirmation、Submission/SubmissionItem、Decision、Issue、AuditEvent；确切命名和约束在 P01 发布。专家改码后的 AI 结果仍标注原待审 HS，不暗示已核查新终值。

## 7. 工作量如何评估

旧 51 项任务的 236～472 小时是按人工熟悉技术栈估算的范围，不能直接换算本轮 Agent 的日历周期。新的任务包保留旧编号映射以核对范围，按以下三项实际记录评估：

1. **工作量**：每包实际 Agent 运行时长/轮次、返工次数、主控审查与集成耗时。
2. **等待**：模板/业务规则、接口权限、专家标注和外部环境分别计时，不混入编码耗时。
3. **完成量**：区分模块自验、集成验收、业务验收；模拟、SQLite、PostgreSQL 和真实 AI 的验证结果分别记录。

先用 P00、P02、P07 完成一次“派发 → 开发 → 回交 → 集成”作为校准样本，再估算下一批。以已通过验收的里程碑汇报进度，不用文件数、代码行数或 Agent 的“完成”描述代替。
